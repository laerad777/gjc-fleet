# GJC Fleet

An **independent local module** that assigns existing GJC runs to multiple nodes. It provides a CLI and TypeScript API, SQLite-based reservation and duplicate prevention, exact Git inputs, a public Coordinator connection, question forwarding and result collection. It does not create a new coding agent or a resident job server.

**The current state is partial implementation and verification, not completed acceptance of the whole Fleet.** Real two-node runs, real workflow approval consumption, Windows runs and recovery from every failure have not been accepted yet. For licenses and provenance see [NOTICE.md](NOTICE.md); for the boundary of future incorporation see [UPSTREAM.md](UPSTREAM.md).

## Setup and installation

- Requires Bun 1.3 or later, Git, and the existing public GJC CLI on each target node. The Bun version actually checked is kept in the verification record.
- There are no npm runtime dependencies. The type-check devDependencies are `typescript`, `@types/bun` and `@types/node`; you need `bun install` to run `tsc` and the CI type check. No global install is needed.
- On macOS and Linux it uses `openat` pinned to a handle; on Windows it uses kernel32 reads and ntdll handle-relative publishing. There is real Windows native/DACL, backup and full-suite evidence, but this is not every ACL, adversarial inode CAS or full operational acceptance. Before a read, the reader requires the final canonical file path to be exactly equal to the held root plus the verified request parts. It also refuses a junction alias that points to `.gjc` inside the root, and fails conservatively on case/8.3 spelling aliases. Controlled contracts and real OS evidence are kept separate.
- It can use an already authenticated SSH connection. This module does not change keys, trust registration, services, providers/models or credentials.

```sh
bun src/cli.ts --help
bun test test
bun run build
```

`bun run build` produces executable code for Bun in `.local/build`. It does not download dependencies or deploy. It is different from the static type check.

## First, check the state of the existing node

### Termination without an execution receipt, and late receipts

When the public read_turn of the exact session and turn, and the `turn.result` of the original runtime command, show the same fact "finished but the receipt is missing/absent" in two consecutive applied polls at least 60 seconds apart (it restarts if another applied poll or an unknown poll lies between them), the task is confirmed as `failed` and the reservation is released once. `result.settlement` carries `failed_without_receipt` or `ended_without_receipt`, the receiptState, a cause with control characters removed, credentials masked and capped at 1 KiB, `settledAt`, and `lateObservationUntil`. A completed turn is confirmed only for an idle `completed` session with SDK `live:true`, or an ended/errored session that has `ended_at`. Verification and tests are refused; `result TASK_ID` (no ARGV) can collect the result only as unverified evidence (`not_run`). Clawhip collect is refused from the start.

For 24 hours after confirmation (`LATE_RECEIPT_WINDOW_MS`, measured by the Fleet time of the confirming poll), `poll` re-reads, read-only, only the same session and turn and the runtime command/turn at the time of confirmation. If a receipt that the normal path accepts (terminal_ok or failed) appears for that exact command, it records a `late_receipt_contradiction` audit event and `result.lateReceipt` (status, digest, terminalAt, structured outcome, ID, observation time) and shows them in the dashboard and CLI (`show`, `tasks`, `poll`). The phase stays `failed` and the released reservation is not taken again. In a `deferTerminalRelease` store, the confirmed slot is kept until resource return (`return`, `return-override`) or archiving; during that time late receipt recording and acceptance behave the same and do not change the reservation state. Observation stops at whichever comes first: the first record, the end of the window, or archiving, and an archived task is not observed again. A receipt from a different turn, session or command is not recorded.

`bun src/cli.ts --db /absolute/own/fleet.sqlite task accept-late-receipt TASK_ID --reason 'basis for confirmation'` (API `fleet.acceptLateReceipt(id, {reason}, actor)`) re-confirms the same digest with a new exact lookup, only for a recorded late `terminal_ok`, then audits `late_receipt_accepted` and moves the task to `completed_unverified`. Success comes only when the ordinary verifier `result TASK_ID ARGV.json` later passes. A late `failed` receipt cannot be accepted. A confirmed `failed` task can be archived under the existing rules, and `archivedFrom.result` keeps the settlement and lateReceipt.

### Settlement evidence table: evidence × receipt → phase / reservation / count

On every observation, `poll` decides the phase only by the table below (first match from the top). "Count" is the dashboard `summary`. A reported failure (public turn `failed`, runtime record `failed`, a failed outcome, or a non-empty runtime `error` such as `agent_error` or `prompt_deadline_exceeded`) is by itself neither evidence that the turn ended nor evidence of a result.

| Evidence | runtime receipt | phase | Reservation | Count |
|---|---|---|---|---|
| Pending question | irrelevant | `approval_required` | kept | not in activeTasks |
| Two consecutive observations (≥60 s) of the same "ended, no receipt" | missing/absent | `failed` (`result.settlement`, 24-hour late-receipt observation) | released once | failedTasks |
| A durable `failed` receipt for the exact command (code/provenance the normal path accepts, confirmed delivery ID) | present, failed | `failed` (executionTerminal) | released once | failedTasks |
| A successful terminal condition (agent_end, live idle SDK, complete question lookup) | present or matching | `failed` if the execution state is `failed`, otherwise `completed_unverified` | released (kept until resource return when `deferTerminalRelease`) | failedTasks / unverified |
| A reported failure, none of the above | missing/absent/incomplete | `completed_unverified` (executionTerminal false), reason `execution_failure_reported_end_unproven` | kept | `failureReportedTasks`, within unsettledTasks |
| Any other public turn `completed`/`cancelled`/`superseded` | incomplete | `completed_unverified` (executionTerminal false) | kept | `provisionalTasks`, within unsettledTasks |
| Anything else | irrelevant | `active` | kept | activeTasks |

`activeTasks` is the number of tasks in a really running phase (preparing, dispatching, active). A `completed_unverified` task that holds a slot without termination evidence is counted separately as `unsettledTasks` (`approval_required` is not included), and `provisionalTasks` and `failureReportedTasks` are a breakdown within it. A failure report without evidence that the run ended is counted neither as `failed` nor as an unverified result (`pipeline.outcome.unverified`), and the dashboard shows it as "Failure reported · end not confirmed". If one of the two failure rows above holds for the same error, the task is settled as `failed` in that poll. The reason of a reported failure is cleared when an observation or settlement that does not report a failure arrives.

Rows written by an older tree with `completed_unverified`, held, executionTerminal false are not changed by reading alone. The next normal `poll` re-judges them with this table, and confirmation still needs the evidence above.

### Classification of create refusals

A `gjc_coordinator_start_session` refusal (`tool_refused:<reason>`) is classified only by what the reason code proves (`CREATE_REFUSAL_CLASSES` in `src/rpc.ts`; a code not in the list defaults to `unknown`).

| Reason code | Class | Result |
|---|---|---|
| `spawn_failed` | `failed_before_effect`: no session was created | A refusal receipt on the create claim, phase `failed` (executionTerminal, not verifiable), reason `tool_refused:spawn_failed`, reservation released once, `create_refused` audit (diagnostic `condition:create_refused_before_effect`). If an overlapping start meanwhile recorded `blocked_unknown`, the same transaction also writes `unknown_reconciled` (`blocked_unknown` → `failed`, cause `create_refused_before_effect`) |
| `broker_compensation_unobserved` | `unknown`: it is not known whether the compensating close happened after the session was created | `blocked_unknown` as before, reservation kept, no resend |
| Anything else, a `tool_refused` without a reason, a response body that is not `ok:false` with the same code, or a refusal that has a session ID | `unknown` | Same as above |

The workspace is not deleted (the archive and cleanup paths handle that). After a start that became `failed` through a create refusal, `queue reconsider` stops that round together with `blocked_unknown`. Even if the same node refuses every create, only one task fails per round and the other candidates stay `queued`.

### Verification request conflicts and verification claims without an owner

Preserved verification evidence of the same attempt (a test receipt, the tests of a cached result, a result-test receipt) is immutable, so a request with a different ARGV (`VERIFICATION_CONFLICT`) cannot succeed on retry. The first conflict records `task.verification` (`state:"conflict"`, the requested and preserved ARGV digests, count, first and last time) and a `verification_conflict` audit (`final:true`), and sets an empty reason of the task waiting for verification (`completed_unverified`) to `verification_conflict`. The count and first time cover every conflicting request recorded for that attempt, repeats included. A repeat of an already recorded request (at most 8 distinct request ARGV digests per attempt, `recordedArgvDigests`) only raises the count even if it is not the most recent request; it does not change the first time and writes no further audit. In cases that are not recorded (an archived task, a conflict where the request ARGV is the preserved evidence itself (for example the ARGV in the node verification response differs), a new request beyond 8), nothing is changed and only `result_validation_rejected` is written. A successful verification clears this reason.

A verify-test/result-test claim has an owner lease (owner, pid, host, expiry = claim + 24 hours `VERIFIER_OWNER_BOUND_MS`). When the owner of a claim without a receipt is certainly gone (lease expired, an exited pid on the same host, a finished call of the same process, or for an old claim without a lease 24 hours after the claim), it writes `task.verification` (`state:"owner_gone"`), reason `verification_outcome_unknown` and a `verification_owner_gone` audit once. The test is not run again. Because an approved test process keeps running and may write to the workspace even when the claiming process is gone, `result TASK_ID` for a task with a verify-test that has no receipt continues to be refused as `TEST_UNKNOWN` (the result manifest is immutable, so a workspace that a test is writing to is not collected and pinned). A claim with a live owner is refused as `TEST_UNKNOWN`. If the receipt of the very claim judged ownerless is recorded later (`recordVerification`, `recordOperationReceipt`) or that claim is released as unsent (`releaseUnsentClaim`), the owner was in fact alive, so that `owner_gone` record and the reason `verification_outcome_unknown` are cleared (other reasons stay).

### Receipts are point-in-time records

A row of the `receipts` table is a point-in-time record of the observation that made it, not a projection of the current state. Fleet reads it only for event_id de-duplication, and verification, archiving and late receipt recording do not add or edit rows. So it is normal for the last receipt row to differ from the phase (for example, the last row of a task that was verified successfully is `completed_unverified`). The current state is the task's `phase` and `held` and `core.executionOutcome(task)` (null for no observation, `unsettled` for no settlement evidence, `verified` when verified, otherwise the settled `result.status`). The last column of `tasks`, `resultStatus` of `watch`, and `outcome` of a dashboard task use this value. An external tool that settles from receipts must read the task row.

### Lane progress watching: stalled sessions and sessions that ended but were not observed

`poll`, `watch` (single and `--all-active`), `run --wait` (the watch of the started task) and `queue reconsider` read the GJC session transcript (`<agentDir>/sessions/*/*_<sessionId>.jsonl`) of `active` and `blocked_unknown` tasks from the node, in addition to the existing observations. They run only one read-only command per node over the transport registered for that node (the same destination for an ssh node, this host for a local node): up to 64 sessions, and for a Windows node reached over ssh only as many sessions as keep the remote command at or under 8000 characters so it fits the cmd.exe command-line limit of 8191 (currently 12 with the present script), the rest on the next refresh; a deadline of 20 seconds for POSIX `sh` and 60 seconds for Windows PowerShell; a cap of 64 KiB each on stdout and stderr. They do not run gjc, so they do not attach to a session, send a prompt or start a broker. What they read is only the file modification time, the node time, the type/role/stopReason of the last entry, the number of unfinished parallel tool calls, and the stopReason of the last message line of the read window when it is from the assistant; content is not read. Each task is read at most once per 60 seconds (by the stored `progress.observedAt`, shared by several callers). Node reads run in parallel per node and each call waits for its read, so a single unreachable or unresponsive node makes `poll`, each refresh of `watch` and `run --wait`, and `queue reconsider` (including a run that started no task) take longer by up to that deadline in the worst case (20 seconds for a POSIX node, 60 seconds for a Windows node).

The result is the `progress` record of the task (verdict `progressing`, `stalled_model`, `stalled_tool`, `finished_unobserved` or `unknown`, lastProgressAt, lastEntryKind, observedAt, idleSeconds, diagnostic). It is stalled when the transcript is not written for **more than** 8 minutes waiting on the model (`--stall-model-seconds`, default 480) or 40 minutes of tool execution (`--stall-tool-seconds`, default 2400). Exactly at the limit it is still progressing. The age is measured by node time, so it does not depend on clock skew between the hub and the node. It writes a `progress_stalled` audit event once when a stall episode starts, and a `progress_recovered` audit event (recovery time `recoveredAt`, merged re-stall count `coalesced`) when it has not stalled again within 1 hour after recovery. A stall within 1 hour after recovery is merged into the same episode and is not audited. If only non-message entries (`model_change`, `custom` and so on) follow a finished assistant line, it is still a finished turn (`finished_unobserved`). For `finished_unobserved` of an `active` task, `watch` (single and `--all-active`) and `run --wait` run the ordinary tolerant observation (`inspect`) immediately once per same transcript state (retry after 5 minutes). That observation runs only for a task that the watch is still watching; a task whose watch already stopped from consecutive read failures (5) is read and shown in `--all-active` but not observed again. The refreshes of `poll` and `queue reconsider` only detect and do not observe, and a `blocked_unknown` task is read and shown but is not observed (retries included) by any refresh. If the read window (the last 64 lines) has no line that fixes the number of open parallel tool calls (an assistant or user message or a session header), a tool may still be running, so the tool limit is applied and `pendingToolsUnknown: true` is recorded. Even if the hub clock goes backwards (the stored read issue time is in the future by more than the node read deadline + 120 seconds relative to the new read), the new read updates the record, and a record with a future time is also subject to the 60-second interval limit. If the stored read issue time is in the future of the hub time within that tolerance, the new read is discarded, so it is not read again until the hub time passes that time. It is shown only while the task is `active` or `blocked_unknown`: `tasks --compact` (the 7th column `STALLED_MODEL:<seconds>s`, `STALLED_TOOL:<seconds>s` or `FINISHED_UNOBSERVED`, only when it is a display target), `progress` of `show` and `tasks`, `progress` of `observability` (only when there is a record) and its warning, and the `progress` field of the dashboard status JSON. Fleet only detects and guides the operator; it does not terminate, close, resend or reassign sessions. Retention: the `progress` record on the task row is one per task (overwritten, about 1.1 KB or less) and is cleared when the task reaches a terminal state (`succeeded`, `failed`, `cancelled`, `archived` or execution end). The `progress_stalled` and `progress_recovered` audit events are not erased because the audit table is append-only. A stall and recovery pair happens at most once per (1 hour + read interval) regardless of the limit, so the worst case is under 48 per task per day, and a session that stays stalled or keeps stalling again within 1 hour after recovery is one episode (at most 2 records).

### Move unknown and failed tasks from the active view to the archive history

`bun src/cli.ts --db /absolute/own/fleet.sqlite task archive TASK_ID [--notes /absolute/notes.json]` moves to `archived` only `blocked_unknown`, `cancel_unknown`, `failed`, and a `dispatching` task that is pending because a preparation refusal proving that the node ran nothing (`before_send`) is the only thing left on the current attempt (only the receipt-less `operator-run` claim of the `run` that started that attempt may accompany it). The latter is the operator release path for that refusal; the refused claim is not resent, and after archiving no preflight is sent either. It does not cancel the run or terminate the session. It does not delete the task, result, task intent or audit record; `archivedFrom` keeps the original state, reason and result, and only the held reservation is released. It drops out of the active list and the pipeline count and can be seen in the collapsed archive history of the dashboard.

The API is `await new Fleet(store).archive(id, {notes?, operatorOverride?, noSessionConfirmation?}, actor = "operator")`. At archive time Fleet itself queries `sdk session list --scope all --json` using the task's recorded `nodeSnapshot.sdkTransport`, and blocks auto-starting a local or SSH remote broker. It is not replaced by the current transport in the node registry. The submitted JSON, time and list are not evidence of query authority, and notes are only an annotation for audit. A direct `store.archive` call needs a one-time Fleet-internal authority, so public evidence JSON is refused. It requires a successful full broker list, an explicit live/locator, and a query start time on the Fleet side within 5 minutes. It refuses if there is a live original sessionId or a task/attempt ID locator. The audit event keeps the node ID, the actual command, the SHA256 of the raw response, the Fleet time, the actor, the notes and the exception reason. A repeat call with the same request and actor queries again but does not create a duplicate event. The query is refused if it exceeds the 15-second timeout, 8 MiB of stdout or 1 MiB of stderr.

If a retired node has neither a sessionId nor a create receipt, `node_retired` alone is not enough. You additionally need `--no-session-confirmation never_started --no-session-reason 'basis for confirming nothing was created'` or `--no-session-confirmation create_outcome_unknown_operator_confirmed --no-session-reason 'basis for confirming the create outcome is unknown'`. The API's `noSessionConfirmation` has the form `{kind, reason}` and both reasons are kept in the audit history.

If there is neither a sessionId nor a create outcome receipt, you must specify `--operator-override never_started --reason 'basis for confirming it was not run'` or `--operator-override create_outcome_unknown_operator_confirmed --reason 'operator basis for confirming the create outcome is unknown'`. If there is no registered node, it is not allowed automatically, and only the `--operator-override node_retired --reason 'basis for confirming the node is retired'` path is allowed. This retirement exception is an administrative judgment made on the operator's responsibility that a remote query is impossible; it is not technical proof that no session exists. On every path the task's non-empty original nodeId is required. schema/user_version 2 blocks reopening by an old writer, and the archived-phase change trigger also blocks an already open old writer from reverting the state. The first write open of an old schema 1 DB migrates only metadata in a transaction and keeps the existing history. The trust boundary is the registered SDK executable/SSH and operator authority; a malicious transport itself or direct tampering with the DB is not defended against.

### Operator disposition of unverified completed tasks (`task dispose`)

For `completed_unverified` (execution end confirmed), the only way to close it so far was `result TASK_ID ARGV.json` (collect the result again from the node and, if the operator command passes, succeeded). `task dispose` instead leaves an **operator record** and moves the task to the existing terminal state `archived`. It is not Fleet verification and does not make the task succeeded.

```sh
bun src/cli.ts task dispose TASK_ID --as deployed --commit SHA --reason TEXT
bun src/cli.ts task dispose TASK_ID --as superseded --by OTHER_TASK_ID --reason TEXT
bun src/cli.ts task dispose TASK_ID --as review-recorded --subject TEXT --verdict clean|not-clean --reason TEXT
bun src/cli.ts task dispose TASK_ID --as discarded --reason TEXT
#   Each form takes [--node-retired REASON] [--actor NAME] [--dry-run]
bun src/cli.ts task dispose --batch ITEMS.json [--actor NAME] [--dry-run]
bun src/cli.ts tasks --disposition deployed[,superseded,review-recorded,discarded] [--compact]
```

- `deployed` is a **record of the operator's statement** that "this task was applied as commit SHA". Fleet cannot see the code repository, so it only records the commit (7 to 40 hex digits, stored in lowercase) and does not verify it. The `--by` of `superseded` must be another existing task (any state), and a circular supersede relation is refused. `review-recorded` is a review verdict with nothing to deploy, and `discarded` is an unverified discard such as a rehearsal. Every record carries the fixed `statement` (for example "Operator record: ... Not succeeded.") and `verifiedByFleet: false`, and `show`, `tasks` (`disposition` in JSON, the extra last column `disposed=KIND...(operator-record,not-verified)` of `--compact`) and the dashboard archive history (for example "Recorded as deployed · operator record, not verified by Fleet") show the same meaning.
- It uses the existing archive path as is. `archivedFrom` keeps the original phase, reason and result reference (settlement included), and, exactly like archive, it queries read-only `sdk session list --scope all --json` once (broker auto-start blocked) with the task's recorded SDK transport and checks it with the **same code** as archive. If the original session is alive (idle included; return an idle session first with `return`) it is refused as `ARCHIVE_LIVE_SESSION`, an incomplete list as `ARCHIVE_EVIDENCE`, and an in-progress `run` lease as `ARCHIVE_IN_PROGRESS`. A disposition never releases a reservation and does not judge the session list in order to release one. A task that still holds a reservation (for example one waiting for return on a deferTerminalRelease hub) is refused as `DISPOSE_RESOURCE_UNPROVEN` before any node query, regardless of the list and of `--node-retired`, and the reservation stays under the existing resource return rules. First return the reservation with `return TASK_ID` (proves the session is gone) or the audited `return-override TASK_ID JSON`, then dispose. A `completed_unverified` task whose execution end is not confirmed keeps holding a slot, so it is refused as `DISPOSE_NOT_TERMINAL` before any node query; if a resource-return pass is running on that node, `DISPOSE_RETURN_IN_PROGRESS`; another phase, `DISPOSE_PHASE`. A task of a node removed from the registration needs `--node-retired REASON` (the same operator administrative judgment as the `node_retired` exception of archive).
- It does not read, re-collect, rewrite, externalise or delete the result body. A `result`/`result --test` that was already in progress when the disposition committed is refused with `ARCHIVED_TASK` at its write stage (`saveResult`, a verification receipt, a `verify-test`/`result-test` claim and receipt, `verifyResult`), recorded as `refused`, with a non-zero exit code, and nothing is written to the disposed row (a collection or verification command already run on the node is not undone and its output is not kept). The result stored in the row (an inline manifest or an externalised reference) is moved byte for byte and the blob is not opened. If the stored row is not in canonical form it is not rewritten and is refused as `DISPOSE_ROW_FORM`. So even on a v2 DB with the result store switch on, no externalised write, ladder step or `user_version` change happens (a task archived without disposition is not moved by `migrate results`, but the inline result of a disposed task is a target of an explicit `migrate results --apply` exactly as before disposition).
- Re-running the same request by the same actor does not query the node again, returns `already_disposed` and writes nothing. A different disposition, reason or actor, or a task archived without disposition, is refused as `DISPOSE_CONFLICT` and is not overwritten. `task archive` on a disposed task is `ARCHIVE_CONFLICT`. The audit history has one `archived` event with the `disposition` (kind, fields, actor, time, request digest). A Store-stage refusal is recorded as `refused` (Store.transaction/record diagnostic) like other Store refusals. But refusals raised in Fleet before the Store transaction, as with `task archive` (`DISPOSE_INPUT`, `TASK_NOT_FOUND`, the `ARCHIVE_NODE` registration check, a failed session query `ARCHIVE_TRANSPORT`/`ARCHIVE_OUTPUT_LIMIT`/`ARCHIVE_QUERY`, and a list that cannot be interpreted) are not recorded and are reported only as a command error (the item's `code` in a batch). `--dry-run` writes nothing, refusals included, and prints what would be done.
- `--batch` is a list of `[{"taskId","as","reason","commit"|"by"|"subject"+"verdict","nodeRetired"?}]` (at most 500, the same names as the CLI flags). If there is even one usage error such as a format error or a duplicate taskId, nothing is applied and the exit code is 1. Otherwise each item is applied independently and `{ok,dryRun,total,refused,items:[{ok,taskId,outcome,code?,message?}]}` is printed; it continues with the rest even when some items are refused and returns 0 only when all succeed.
- A disposed task is archived, so `run`/`run --wait` of the same caller/key only reports 4 (`failed`) exactly as for an archived task and does not start it again, and `watch --all-active` does not observe it.
- API: `await fleet.dispose(id, {kind, reason, commit?|supersededBy?|subject?+verdict?, nodeRetired?}, actor = "operator", {dryRun?})`, `await fleet.disposeBatch(items, actor, {dryRun?})`.

```sh
gjc --version
gjc sdk diagnostics broker --json --timeout-ms 3000
GJC_SDK_BROKER_AUTOSTART=0 gjc sdk session list --scope all --attach-only --agent-dir /absolute/actual-agent-directory --json
gjc mcp-serve coordinator --check --json --attach-only
```

A successful catalog does not mean the model or the real run is ready. `absent` in the diagnostic applies only to the agent directory that call selected, and `unsupported` means the diagnostic feature is not supported, not that the Broker is absent. If the public session list of the actual agent directory succeeds with `source:broker`, reaching that Broker is confirmed, but model readiness and task success are verified separately. You can record an independent query with `bun scripts/live-check.ts --agent-dir /absolute/actual-agent-directory`. For SSH, give the existing alias and `--ssh-shell posix|cmd` explicitly. This module does not auto-start a Broker or restart an existing service.

## Explicit local node registration

It configures only the repositories you have allowed and the dedicated workspaces. The source repository must already contain the exact commit. You do not need to commit into the module's own empty Git repository.

```sh
mkdir -p .local
bun scripts/local-node.ts sample /absolute/repository /absolute/fleet-workspaces local --agent-dir /absolute/actual-agent-directory --model-profile approved-profile > .local/node.json
```

The default output is disabled and readiness-unverified. Add `--attest-ready` and generate the config only for a node whose existing Broker/model/public-contract readiness you have checked yourself. This is the operator's explicit readiness declaration, not evidence that an automatic health check succeeded. If a specific model is required, state the node's `models` list and the task's `required.model`. Do not put secrets in the config; keep the node's existing credential boundary.

```sh
bun src/cli.ts node add .local/node.json
bun src/cli.ts node list
bun src/cli.ts node enable local
bun src/cli.ts node drain local
```

`enable` does not turn readiness-unverified into ready. drain/disable block new reservations, and also refuse, at send time, with `NODE_NOT_ADMISSIBLE` any new send (the source/input package of preflight/prepare, session creation, prompt) of a task that is already reserved but not yet sent (nothing is sent or claimed and the reservation stays held; after enabling again it continues with the same attempt). Observation, answers, cancel and result collection of a started run are not blocked, and an existing run is neither moved nor cancelled. If the route used by that task's send (id/os/arch/transport/workspaceTransport/workspaceRoot, `roots[repoId]` of that task's repository, and sdkTransport only when it is in the snapshot) differs from the reservation snapshot, it is refused with the same code. Adding or changing the root of another repository, or adding an sdkTransport that was not in the snapshot, is not a reason for refusal. This route-change refusal is not cleared by enable/disable and remains until that route is restored exactly or the task is archived. Admission of a new run is decided by measured resource headroom; the global/node concurrency caps keep only metadata and are not enforced. `--db` and `--cap` must be used with the same values in every command.

Task JSON example (enter the full SHA of the real repository as the commit value):

```json
{
  "schemaVersion": 1,
  "key": "my-task-1",
  "caller": "operator",
  "repoId": "sample",
  "baseCommit": "0000000000000000000000000000000000000000",
  "prompt": "Make only the requested changes and run the tests inside this workspace. Do not install, commit, push or deploy.",
  "required": {"os": "darwin", "operations": ["coordinator.prompt"]},
  "preferences": ["local"]
}
```

The 0 values above are an input-format example, not an executable commit. Without a real commit, workspace preparation is refused. A branch/latest or a copy of a whole dirty directory is not used as input.

```sh
bun src/cli.ts --local-node-id local submit .local/task.json
bun src/cli.ts --local-node-id local start TASK_ID
bun src/cli.ts --local-node-id local queue reconsider 10
bun src/cli.ts show TASK_ID [--reviews]
bun src/cli.ts poll TASK_ID
bun src/cli.ts events TASK_ID
bun src/cli.ts --local-node-id local result TASK_ID .local/test-argv.json
bun src/cli.ts return TASK_ID
bun src/cli.ts return-override TASK_ID .local/approval.json
bun src/cli.ts return-unblock NODE_ID .local/approval.json
```

`queue reconsider [LIMIT]` explicitly re-evaluates a snapshot of unattempted queued tasks (default 10, maximum 100). It measures resources again for each candidate, repeats submit's readiness checks and resource admission, and starts only reservations won by this caller. Missing/stale samples fail closed; `--resources` is subject to the same freshness checks. Task IDs, request keys and input digests are retained. Every selection is audited (a rejection whose verdict-deciding reasons equal the task's recorded rejection is counted on the task instead of appending another row; see below), and the pass stops after a start returns `blocked_unknown` or settles `failed` by a create refusal. The library export is `reconsiderQueue(fleet, asyncSampleProvider, { localNodeId, limit })`; callers must supply fresh node samples, not a policy override. Repeated passes never replay existing attempts. Dashboard observation remains read-only: watching or refreshing a page does not authorize starting queued work.

### Queue: capacity waiting, unplaceable, and withdrawal

A selection that finds no node leaves a small `placement` record on the queued task. For each exclusion reason, a single table in `src/core.ts` (`PLACEMENT_REASON_CLASSES`) separates reasons that can clear by themselves (transient: no resource measurement or a delayed one, too little CPU/memory/disk headroom, node health, `draining`, `unreachable`, SDK/model not ready, old slot reasons and so on) from reasons that clear only by an operator configuration change (structural: `repo_unavailable`, `manual_node_mismatch`, `disabled`, `os_mismatch`, `arch_mismatch`, `model_unavailable`, `model_profile_unavailable`, `operation_unavailable:*`, `probe_platform_mismatch`). A new reason not in the table is treated as transient, so a task cannot become unplaceable by mistake. A task pinned to one node (`required.nodeId`) is `unplaceable` if that node has a structural reason, regardless of other nodes. A task that is not pinned is `unplaceable` only when every excluded node has at least one structural reason; otherwise it is `waiting` (capacity wait).

- The record is `{verdict, since, checkedAt, rejections, exclusionsDigest, nodes, blocking}`, and `blocking` keeps the pinned node first, then up to 8 nearby nodes (fewest structural reasons first) and up to 8 reasons per node. There is no schema change or new table (it is a new field in the task row JSON, ignored by older builds), and the record is cleared when the task is placed.
- `show`, `tasks` (`placement` in the JSON, operator wording in `summary`), `tasks --compact` (an extra column `waiting="..."` or `unplaceable="..."`) and the `queue reconsider` output distinguish the two states and show the reason of the pinned or nearest node in operator wording (for example `unplaceable: NODEB does not serve repository example-repo; ...`). The prompt is not printed. The dashboard summary has a separate `unplaceableTasks`, and an unplaceable task is shown not in the in-progress list but in the "Results / status check tasks" group as "Unplaceable · operator action needed", and it is excluded from the "Waiting" count of the pipeline chip.
- If the reasons that decide the verdict are the same, no new selection audit row is written; only the task's `rejections` and `checkedAt` and `blocking` (the latest full reasons) are updated, and `since` stays. The reasons that decide the verdict are the verdict, the pinned node, and for each node that has a structural reason only that structural reason (for a preflight bundled reason `<stage>:<code>+...`, only the structural code), and for the other nodes all reasons. So even when node-health gating is on and the CPU, memory or disk state of another node already excluded as structural changes, no row is added and the "unplaceable since" time does not move. One row is left each time the reasons that decide the verdict change. So the `admission/admission_rejected/no_eligible_node` count of `observability` is the number of rejection records left in the audit (a repeated rejection for the same reason counts as 1), and the repeat count is in the task's `placement.rejections`. The exit code table is unchanged (`run` still returns 2 `queued`).
- In `queue reconsider LIMIT`, an unplaceable task does not take the place of a waiting task. Waiting tasks use up to LIMIT-1 places in queue order (all LIMIT places if there is no unplaceable task), and the remaining place re-checks the unplaceable task that was checked longest ago. A task the pass skips without a reservation attempt (a role task while the work-unit switch is off) is dropped from re-checking and so does not take that place. So with a LIMIT of 2 or more, after an operator adds a repository or turns a node back on, that task is placed by itself. If both kinds exist with LIMIT 1, the waiting task is chosen, so LIMIT 1 does not re-check an unplaceable task while there is at least one waiting task. The daemon's read-only queue pass writes no selection audit, so it is unchanged.

```sh
bun src/cli.ts queue withdraw TASK_ID --reason "NODEB does not serve example-repo" [--actor NAME]
```

`queue withdraw` takes back, with a single command, a queued task that was never placed (no attempt ID, node snapshot, session, workspace, reservation or operation row, and nothing sent to a node), whether it is unplaceable or waiting for capacity. It changes only the local DB and does not connect to a node. The task moves to the existing terminal phase `archived` (`archivedFrom` keeps `queued` and the reason; in the exit code table it is 4 `failed`), and a `withdrawal {actor, reason, at}` and one `withdrawn` audit line are left. The reason and the actor (default `operator`) are each at most 200 characters. Running it again writes nothing and returns `already_withdrawn`. It is a single write transaction, so it splits atomically against a concurrent reserve: a task withdrawn first is not placed (`ARCHIVED_TASK`), and a task placed first is refused with `WITHDRAW_ATTEMPTED` and left to the existing `cancel`/`return`/`task archive` paths. It is fine for the daemon to be running. The other refusal codes are `WITHDRAW_INPUT` (reason/actor missing or too long) and `WITHDRAW_PHASE` (not in a waiting state), recorded as `refused` like other Store refusals. `cancel ID` keeps the session abort/close contract and is unchanged.

`test-argv.json` is a command array you approved directly, for example `["bun","test"]`. It is not run as a shell string. The result test is not run before the end of execution is proven. The result includes the real argv, the exit code, the output and hash, the changed file bytes and hashes, and the patch. `not_run` is not a test success. The result is not applied or run automatically.

A `not_run` result that was already collected without a verification command can also be verified explicitly with the same `result TASK_ID ARGV.json` or `fleet.result(id, argv)`. It does not change the original manifest or the task/attempt, and persistently claims once a `result-test` bound to the original artifact digest, workspace, session/turn and argv. Only if the bytes collected before and after the run match the original artifact does it keep a separate verification receipt, and only the tests/status of the returned result are built from that receipt. The original stored manifest stays immutable. A later query of the same command reuses the receipt, and a different command or a re-run of an existing unknown test is refused. If the original workspace is gone or the bytes differ, this is not treated as verification success. If there is no receipt because a response was lost or bytes changed during the run, the claim is not reset and is not bypassed with a different command. However, when it is proven that the verification command was not delivered to the node (the helper refused with `before_send` in the workspace path / identity file check, or the helper run itself failed, or in `result-test` the read-only collect/compare before the verification command failed), only that exact receipt-less `verify-test`/`result-test` claim is released (audit `operation_claim_released`), so if a temporarily missing workspace path is restored, the same command is verified once without operator action. `stop` also claims only after the Coordinator connection and the stop tool are confirmed. **`verified` in a report artifact is only the receipt of the stated command; it is not a CLEAN verdict of an independent review, success of the model task, or deployment approval.**

### Export completeness and nested repositories

Result `status` describes command evidence only: `verified` means all recorded commands exited zero, **not** that all workspace content was exported. New manifests always include `exportComplete`, `exclusions`, `ignored` and `junk`; any exclusion makes `exportComplete:false` and the exclusion entries are its reasons.

**Discovery.** Nested repositories are found by walking the workspace filesystem itself, independent of `git status` and of every ignore source (in-tree `.gitignore`, `info/exclude`, `core.excludesFile`, global excludes). Tracked, untracked and ignored locations are therefore treated alike. A directory containing any `.git` entry (directory, worktree/submodule file, or symlink) is a `nested_repository` root. A base commit holding a gitlink is refused at preparation (`nested_repository`), and the worker's index is never read, so collection produces no `gitlink` root (that reason is still accepted in manifests of earlier releases). The walk never follows symlinks, never enters the outer `.git`, never descends into a found repository root, reads no file bytes, and fails closed with `workspace_scan_limit` beyond 2000000 directory entries (`WORKSPACE_SCAN_LIMITS`; no depth is bounded, as Git bounds none). The bound counts the directory entries Git itself traverses: a directory Git reports ignored (dependency and cache trees such as `node_modules`) is still walked for nested repositories, but its contents are not counted, as Git never enters it; to recover, remove or move large trees that are not ignored out of the workspace (or ignore them) and collect again. Every 100000 listed entries the walk asks Git (`check-ignore`, which reads only rule files the walk already checked) which directories it found are ignored, and keeps no listing of those; once more than 500000 entries were listed below ignored directories, an ignored directory holding no base-tree entry is no longer walked (`IGNORED_SCAN_LIMITS`). A directory the walk cannot read (no permission, or a path too long for the platform) below such a directory is not walked either (an ignored directory that cannot itself be read is not below one). Each directory not walked is withheld as one `nested_repository` exclusion at its outermost ignored ancestor holding no base-tree entry (nested repositories there cannot be ruled out), so the export is incomplete and needs export review; anywhere else an unreadable directory fails closed with `workspace_scan_unreadable` (no host path in the error). Nothing at or beneath a root enters file artifacts or the binary patch, including outer-tracked changes and deletions. Parent roots subsume children. Each root has exactly one sorted exclusion `{path, reason, outerTrackedEntries}`; reasons are only `nested_repository`, `ignored_out_of_tree` and `unlisted` (below; `gitlink` from earlier releases). The count is the number of base-tree entries at or beneath the root; it is not the number of files inside the nested repository. Limits: 1024 exclusions, 100000 per count. Paths use the existing portable safe-relative rules; duplicate, case-colliding, overlapping (except a repository root inside an `ignored_out_of_tree` directory), unsorted, malformed and artifact-overlapping entries are rejected, also on old manifests (only absence is legacy).

**Git never enters a nested repository.** No Git process traverses the workspace before the walk has finished. Every repository root it found, and every directory shaped like a bare repository (`HEAD`, `objects/`, `refs/`, no `.git`) that holds no base-tree entry, is kept out of Git's traversal with `:(top,exclude,literal)` pathspecs, so Git never opens, lists or follows anything at or below it: not a `.git` directory, not a `.git` file naming a Git directory elsewhere (even outside the workspace), not a bare repository's hooks or config. The walk never follows a link, but Git follows a Windows junction: for a junction to a directory holding `.git`, Git probes that `.git` (even outside the workspace) and reports the junction as a repository. Collection then refuses with `unsafe_result_entry:link`; no bytes below the junction are exported. A bare-shaped directory is reported as a `nested_repository` exclusion like any other root. A `.gitignore` or `.gitattributes` that is a FIFO, socket or device (Git would block on it) in a directory Git may read it in, and a base-tree path that has become one (Git cannot hash it), refuse collection with `unsafe_result_entry:special_file` before any Git process traverses the workspace; such a rule file in a directory an in-tree `.gitignore` ignores and that holds no base-tree entry is never opened by Git and does not refuse (decided with `check-ignore` on its directory, shallowest first); a nested repository whose name is not UTF-8 cannot be spelled as a pathspec and refuses with `unsafe_result_entry:repository_name` (both `unsafe_path`). Symlinked rule files are not followed (Git opens them without following links). Because a worker that is still running could plant such an entry after the walk, every Git process over the workspace is also bounded (`COLLECTION_GIT_TIMEOUT_MS`, 5 minutes) and killed on expiry (`git_failed`).

**Path identity.** Walk-derived spellings (what the disk holds) and Git-derived spellings (what Git reports; on macOS Git precomposes to NFC while APFS may hold the NFD spelling, and case-insensitive volumes resolve case variants) are never compared byte-for-byte. Every comparison between them uses one canonical key per path component (`pathKey`: Windows trailing dots/spaces removed, Unicode NFC, case folded), in the collector (boundaries, rule directories, tracked counts, every view) and in `validateResult`. Each exported file is additionally checked by filesystem identity: if any directory on its path is a discovered repository root (device and inode), it is withheld, which also covers aliases no key can express (Windows 8.3 short names). A boundary is reported under Git's spelling when exactly one exists; every spelling is excluded from the patch. Two exportable Git names for one key cannot be matched to one disk entry: all of them are withheld and counted as `unlisted`. The walk addresses entries by their exact bytes (a directory name that is not UTF-8 is listed as raw bytes), and a repository root whose name is not portable is withheld and counted as `unlisted` at its nearest portable ancestor instead of aborting collection.

**Trust model (collection reads no worker-writable Git state).** At preparation, before the worker exists, the node records a collection snapshot in `<workspaceRoot>/.collection-snapshots/<task>-<attempt>.{json,index}` (outside the workspace) and binds it to the identity (`collectionSnapshot`, the SHA256 of the JSON): the base commit, the source repository's object format and object store, the collection-relevant configuration (`core.autocrlf`, `core.eol`, `core.filemode`, `core.ignorecase`, `core.precomposeunicode`, `core.symlinks`, `diff.*` and the other keys of `COLLECTION_CONFIG_KEYS`; any other value refuses preparation with `collection_config_unsupported`), the operator's ignore rules as text (the shared `info/exclude`, the effective repository-selected `core.excludesFile` with every scope and include, and the node's own global/system excludes file, `includeIf` conditions evaluated on the source repository at preparation), the index of the fresh checkout (exactly the base tree, so the in-tree `.gitignore` files at base are part of it) and the workspace root's device and inode. Collection never reads the workspace's `.git`, administrative directory, index, HEAD, refs, config, hooks, `info/exclude` or the source repository's configuration. It walks the workspace by filesystem identity (no symlinks followed, nested repositories not entered) and runs Git only in a throwaway node-created repository in the OS temp dir (`GIT_DIR` there, the workspace as `GIT_WORK_TREE`, no system/global config, `HOME`/`XDG_CONFIG_HOME` inside it, `HEAD` the base commit, objects from the source store as an alternate, the snapshotted index and rules, configuration written from the snapshot alone). The export is the workspace's files against the base commit: worker commits, branch switches, index edits (`git add`, `git rm --cached`, staged gitlinks), `core.worktree`/`extensions.worktreeConfig`, repository `core.excludesFile`, includes, a repointed `.git` file or `commondir`, and edits to `info/exclude` after preparation change neither what is exported nor what is withheld. A snapshot that no longer matches its digest, or a workspace root that is no longer the prepared directory, refuses collection (`collection_snapshot_mismatch`, `workspace_identity_mismatch`; typed `identity_mismatch`); a source repository whose store no longer holds the base tree refuses with `source_repository_missing` (`identity_mismatch`). An identity prepared before snapshots existed collects from the base tree and the source repository's rules read at collection. Operator ignore rules must therefore be in place before a task is dispatched: a rule added to the source repository afterwards is indistinguishable from a worker edit and is not applied to that task. See DESIGN.md for what stays worker-controlled by design.

**Ignored paths: full Git semantics.** The export never contains an untracked path Git ignores under the operator's rules: the in-tree `.gitignore` files the workspace holds now (at every level, with `!` negation and Git's precedence between sources), the snapshotted `info/exclude` and repository-selected excludes file, and the node's own excludes file (`core.excludesFile` of the node's global/system configuration, else `$XDG_CONFIG_HOME/git/ignore`, or `$HOME/.config/git/ignore` when `XDG_CONFIG_HOME` is unset or empty), both as snapshotted and as it is at collection. The node's live excludes file is resolved with the node's real `HOME`/`XDG_CONFIG_HOME` (all `GIT_*` variables removed, conditional includes evaluated against an empty node-created repository with a detached HEAD); a worker-written `<workspace>/.config/git/ignore` is therefore not an ignore source, and a node excludes file that resolves inside the workspace is refused with `ignore_rules_inside_workspace`. Tracked files win, as in Git: changes to base-tracked files are exported even if an ignore pattern matches them, and a base-tracked file is untracked only by deleting it (exported as a deletion). Every untracked path Git ignores (collapsed to the outermost ignored directory, as `git ls-files --others --ignored --exclude-standard --directory` reports it) is classified explicitly:
- **Ignored by the exported in-tree rules** (decided by a `.gitignore` that is part of the export or the collector's own `.gjc/`, or an out-of-tree-ignored directory whose every entry the exported rules also ignore): outside the deliverable by declaration (build output, caches, dependencies). Not exported, does **not** make the export incomplete, and listed in `ignored: {count, unlisted, paths}`: the exact count of ignored roots (Git reports an ignored directory once and is never asked to descend into it), up to 256 sorted portable paths (directories end in `/`), and `unlisted`, the number of counted roots whose names are not portable (control characters, `\ : * ? " < > |`, trailing dot/space, Windows device names such as `nul`) or beyond the 256 shown. Such names never abort the collection.
- **Ignored only through an out-of-tree source** (`info/exclude`, `core.excludesFile`, global/XDG excludes) or by a `.gitignore` that is not itself exported: the exported rules declare it part of the deliverable, but Git hides it, so it is an exclusion `{path, reason:"ignored_out_of_tree", outerTrackedEntries, source}` and the export is incomplete (`result.exportIncomplete`, operator review below). `source` names the deciding rule file: `info_exclude`, `excludes_file`, `unexported_gitignore`, `unattributed` (an aggregated entry) or `mixed`. A withheld entry whose name cannot be listed (not portable, not valid UTF-8, or two Git names for one disk entry under the canonical key below) is counted in an `{path, reason:"unlisted", count, outerTrackedEntries}` entry at its nearest portable ancestor directory, or `.` (the workspace root) when there is none; portable siblings keep their own entries, and an `unlisted` entry never withholds anything else. Beyond 256 entries they aggregate to ancestor directories. Its bytes are never read or exported. Typical cases are local secrets or editor files in a personal global ignore; review and accept, or add the pattern to the tracked `.gitignore`.
- **OS junk ignored only out of tree** (a file named `.DS_Store`, `Thumbs.db`, `ehthumbs.db`, `desktop.ini` or `Icon\r`): not exported, listed in `junk: {count, unlisted, paths}`, and does **not** by itself make the export incomplete, but only when the node's own excludes file (below) ignores it; a junk name hidden by the worker-writable `info/exclude` or repository configuration is an ordinary exclusion. Any other out-of-tree-ignored file still makes the export incomplete.

**Node excludes.** Besides the effective view (all rules above, in Git's precedence, with the repository-selected excludes file when there was one at preparation, else the node's live one), one view per node excludes file (snapshotted and, when it differs, live) applies only the in-tree `.gitignore` files and that file. An untracked path any view ignores is never exported; a path that only a node view ignores is an `excludes_file` exclusion, so an `info/exclude` negation cannot re-include it. A node `includeIf` condition is evaluated on the source repository at preparation (`gitdir:`, `onbranch:` and `hasconfig:remote.*.url:` see the source repository then) and, for the live view, on an empty repository (no condition on repository state holds); the workspace's Git directory, branch and remotes never select or deselect a node rule.

**Cost.** All Git commands below run in the neutral repository. Collection writes it (a few small files), checks the base tree with one `git cat-file -e`, then the effective view is one `git status --porcelain=v1 -z --ignored=matching` plus one batched `git check-ignore --verbose --non-matching -z --stdin`; the node view is one `git ls-files --others --ignored --directory` (when the node has an excludes file); listings are parsed as NUL streams (256 MiB bound). Out-of-tree-ignored directories are checked against the exported rules with one `ls-files` for all of them. No Git process is started per file or per ignored root, and ignored directories are not descended except by the nested-repository walk. `test/collection-performance.test.ts` holds 50000 tracked files plus a 90000-file ignored `node_modules` to at most 3x the base collector's Git work + 300 ms.

A `.gitignore` that Git itself ignores (for example the `*` self-ignore of `.venv` or `.pytest_cache`) is not exported; whatever its rules hide is reported as `unexported_gitignore` exclusions, so collection succeeds with an incomplete export. Nested-repository discovery is independent of all of this: a nested repository inside an ignored directory is still a `nested_repository` exclusion and makes the export incomplete. Inside an in-tree-ignored directory the directory is also listed in `ignored`; inside an out-of-tree-ignored directory both the `ignored_out_of_tree` directory and the repository root are exclusions; an ignored repository root itself is one `nested_repository` exclusion.

**Task states.** Passing commands with a complete export verify the task (`completed_unverified` → `succeeded`). `result.verificationEvidence` keeps exactly the shape `{manifestDigest, testCount, trust}` every earlier release re-derives and compares on each `result` read, so an older release still reads the result of every task this release verified (complete or accepted); completeness evidence is recorded beside it in `result.exportEvidence` (`exportComplete:true`, `artifactSchema`). Passing commands with an incomplete export leave the task **`completed_unverified`** and record **`result.exportIncomplete`** `{subject, reviewDigest, requiredAt}` (audit `export_review_required`); it is never promoted by re-querying or silently. No phase is added, so every release (including ones that predate export review) opens, lists, runs, archives, backs up and resource-returns such a task as an ordinary unverified completion. Until acceptance nothing persisted is a passing result to an earlier release, which verifies a stored `verified` manifest or a passing result-test receipt on every `result` read: a fresh collection is stored `not_run` without tests (its verifier receipt stays in `testReceipt`), and an explicit verification's receipt is held once, as its result-test claim's `held` field (the task row keeps only `result.exportIncomplete.resultTestDigest`), while that claim stays receipt-less; acceptance moves it to the claim's `receipt`. An older release therefore reads such a task as never tested (`result TASK_ID` exits 0 with `status: "not_run"`), refuses `result TASK_ID ARGV` with `TEST_UNKNOWN` (the original verifier's outcome is retained, never rerun) and never turns it into success. Acceptance writes the evidence back in the shape every release reads (the verified manifest, or the claim's receipt) in the same transaction that verifies the task. Failed or not-run commands are not export-review cases (`completed_unverified`/`failed` unchanged).

**Operator acceptance of an incomplete export.** Use this when the exclusions are legitimate (for example review fixture repositories) and the outer artifact is acceptable without them:

1. `bun src/cli.ts export review TASK_ID` (library: `fleet.exportReview(id)`) prints `completeness`, the exact `exclusions`, `manifestDigest` and `reviewDigest`. `reviewDigest` (`exportReviewDigest(subject)`) covers task, attempt, effective result digest, artifact schema, completeness and the exclusion set.
2. Inspect the excluded paths in the workspace out of band. Accepting does not export them.
3. `bun src/cli.ts export accept TASK_ID REVIEW_DIGEST --operator NAME` (library: `fleet.acceptIncompleteExport(id, {operator, reviewDigest})`). It recomputes the review from retained evidence and refuses with `EXPORT_REVIEW_CHANGED` (exit 1) if the exclusion set, result or attempt differs from the quoted digest, `EXPORT_REVIEW_NOT_REQUIRED` if the task is not awaiting review, and `INVALID_INPUT` for a missing/malformed operator (1-128 of `A-Z a-z 0-9 . _ @ + -`). On success `result.exportIncomplete.acceptance` `{operator, reviewDigest, acceptedAt}` is recorded and the task becomes `succeeded` with `verificationEvidence` `{manifestDigest, testCount, trust}` (the shape above) and `exportEvidence` `{manifestDigest, exportComplete:false, artifactSchema, completeness, exclusions, reviewDigest, acceptance:{operator, reviewDigest, acceptedAt}, trust}` and an `incomplete_export_accepted` audit event (who/when/which digest). Acceptance is immutable; repeating it identically is a no-op and a different operator is refused (`VERIFICATION_CONFLICT`). The low-level `FleetStore.verifyResult` refuses a task with `result.exportIncomplete` (`EXPORT_REVIEW_REQUIRED`); only `acceptIncompleteExport` verifies it.

Without acceptance the task stays `completed_unverified` with `result.exportIncomplete` and no `acceptance`: a visible non-success outcome awaiting the operator. There is no separate decline: leaving the review unaccepted is the decline (the task is never verified; its slot is released by settlement or resource return as for any `completed_unverified` task). `export review` reports `required:true`, `tasks --compact` shows `exportReview:"required"`, `run --wait`/`watch` treat it as settled (exit 0, as for every `completed_unverified` task; see the table below), the dashboard labels it `EXPORT_REVIEW` and counts these tasks (and not as unverified) in `summary.exportIncompleteTasks` and `pipeline.outcome.exportIncomplete`. At the store level too, `requireExportReview` and `acceptIncompleteExport` accept only the subject recomputed from the stored passing result (stored manifest plus retained result-test receipt; otherwise `VERIFICATION_CONFLICT`), and `verifyResult` refuses a stored export that is not complete (`EXPORT_REVIEW_REQUIRED`). Like `verifyResult`, `acceptIncompleteExport` refuses a receipt-less settlement whose late receipt was not accepted (`RECEIPTLESS_UNVERIFIABLE`). With `deferTerminalRelease` the reservation stays held while review is pending and after acceptance until resource return releases it, as for a verified task. Alternatively keep fixture repositories outside the workspace before collection.

**Legacy manifests.** Stored manifests without `exclusions`, `exportComplete` and `ignored` (`legacy-v1`) remain readable; a fresh collection without them is refused with `RESULT_SCHEMA`, on first collection and on explicit verification. Artifact digests are versioned by the schema a manifest was created under: when a cached legacy `not_run` result is explicitly verified, the fresh before/after collections are projected to `legacy-v1` before comparison, so a schema-only difference is never `ARTIFACT_CHANGED`; real byte changes still are. The verification receipt records `artifactSchema` and the `observedExclusions` of the fresh collection (identical before and after, else `ARTIFACT_CHANGED`). Observed complete → `succeeded`; observed exclusions → `completed_unverified` with `result.exportIncomplete`. A stored legacy manifest can hold files an earlier release's collector exported that this collector withholds at a repository boundary (an untracked bare repository, a directory holding a `.git` entry that is not a repository). Files missing from the fresh collection only at or below such a boundary are not `ARTIFACT_CHANGED`: the receipt records those boundaries as `observedExclusions` (completeness `incomplete`), and the task awaits export review. A legacy result whose completeness was never observed (for example an old `verified` manifest) is `unknown` completeness and also awaits export review (review shows `completeness:"unknown"`, `exclusions:null`); tasks already verified before this change keep their recorded verification. Receipts recorded before these fields existed remain valid.

Collection rechecks repository boundaries (a second full walk) as well as HEAD/index/base snapshots, patch and untracked listing. Verification digests include exclusions, counts and completeness for `exclusions-v1` manifests, so a receipt cannot be reused after changing them. These are local command/snapshot checks, not remote attestation or native Windows qualification; the discovery walk observes directory listings without openat anchoring (no bytes are read through it; artifact bytes still use the anchored readers).

**Collection limits.** Unchanged: at most 1,024 exported files, 4 MiB per file and 16 MiB in total (`artifact_count_limit`, `artifact_total_limit`). Collection also refuses, as a whole and with nothing exported (node `output_limit`), a workspace that exceeds any of these: 1,024 exclusions in one manifest (`exclusion_count_limit`; each nested repository root is its own exclusion, also inside an ignored directory such as a package cache of Git checkouts; out-of-tree-ignored entries aggregate to at most 256); a discovery walk over 2,000,000 listed entries (`workspace_scan_limit`; counted outside the trees Git reports ignored, such as `node_modules` and `.venv`, which Git never enters); 256 KiB of repository-root pathspecs (`workspace_scan_limit`); 2,000,000 base-tree entries (`tracked_entry_limit`). On Windows one Git command line may hold at most 32,767 UTF-16 units; a collection whose Git command (repository-root pathspecs included) would exceed it is refused before that process starts (`command_line_limit`), which a workspace with a few hundred nested repositories can reach. The workspace itself is left as it is: remove or move the offending trees, or retrieve the files out of band.

**Upgrading nodes (prepared before collection snapshots).** A workspace prepared by a release before collection snapshots (its `task.workspace` identity has no `collectionSnapshot`) is collected under the source root's rules as they are at collection, exactly as that release collected it; the node returns it as a legacy-v1 manifest (no exclusions or completeness fields), so its completeness is `unknown` and passing commands leave the task `completed_unverified` with an export review until an operator accepts it (`export review TASK_ID`, then `export accept TASK_ID REVIEW_DIGEST --operator NAME`). **Upgrading the hub before the nodes.** A hub reads export completeness and says so on every `collect` (`exportCompleteness: "exclusions-v1"`). A node asked by a hub that does not (a release before it) refuses an export that withholds content that release would have exported (a nested repository with content or tracked entries, a name it cannot list) with `unsafe_path` after collection began, as that release's collector refused a nested repository; exports that withhold nothing that release exported (ignored content, repositories inside an ignored directory, a `.git` marker alone) collect as before. Upgrade hubs first.

**Collection rules (`collectionRules`).** Preparation records the source root's collection configuration (`COLLECTION_CONFIG_KEYS`), shared `info/exclude` and repository-selected `core.excludesFile` text in the workspace's collection snapshot. Every worker on a root can write that root's shared `.git`, so an operator who wants those rules fixed records them in the node configuration: on the node host run `bun src/cli.ts collection-rules REPO` (reads the root only; needs no database) and copy its `collectionRules` object into the node configuration as `collectionRules[repoId]`. Preparation then takes the configuration and rule text from there and never from the root's `.git`; the node's own global/system excludes file is read as before. No worker action refuses a later preparation. When the repository roots of a workspace would exceed the collection limits as separate exclusions (1,024 exclusions, 256 KiB of pathspecs, or the Windows command line), the roots inside an ignored directory that holds no base-tree entry are reported as one `nested_repository` boundary, the outermost such directory; within the limits each root stays its own exclusion. Snapshot pairs (`.collection-snapshots/<task>-<attempt>.{json,index}`) of workspaces that no longer exist are removed by the next preparation on that workspace root.

**Collection snapshot files.** Each preparation (every attempt) writes `<workspaceRoot>/.collection-snapshots/<task>-<attempt>.json` (the rule texts, at most 3 x 1 MiB) and `.index` (an index of the base tree). Every later preparation on the node deletes the pair of each attempt whose workspace directory no longer exists (`<workspaceRoot>/<task>-<attempt>`), so the files are bounded by the workspaces that still exist; nothing else deletes them. A task whose snapshot is deleted can no longer be collected or verified (`collection_snapshot_mismatch`): remove a workspace, or a task attempt's two files, only once the task is archived.

`--local-node-id local` is the operator's explicit declaration that the node is on the same host as this CLI process. Local execution is not allowed merely because the OS/architecture is the same. When you use the local helper directly, specify the same ID not only for submit but also for start/result in a separate process. A remote node sets an authenticated `workspaceTransport`; do not declare a node local and run a remote path from the hub. The transport helper must handle the read-only probe of `src/placement-preflight.ts NODE_CONFIG` and all prepare/preflight/test/collect requests. `preflight` is a side-effect-free request that runs only the checks prepare does before its first effect; it reads only the request, the repository settings (checkout filter and so on) and the commit tree of `baseCommit`, and does not read the working tree of the source checkout. So ignored `node_modules`, symbolic links, nested/linked checkouts and large ignored trees affect the preflight result no more than they affect the prepare result. test/collect also pre-check only the workspace directory itself and the identity file, and collect applies the exclusion rules only to the paths it reads, as before. This request is used only to re-evaluate, at the next start or run, a proven (`before_send`) preparation refusal that is pending (`dispatching`, no workspace) on the current attempt. It is not sent to archived, released or unknown-state tasks. The internal error correlation ID is written to `.node-errors.log` next to the helper code (gitignored; stderr when it is not writable). If it passes, the task proceeds with a new attempt on the same reservation, together with an audit record (`preparation_refusal_cleared`), and a task whose outcome is unknown is never resent. If the re-evaluation does not pass, the attempt stays held and the task reason records `preparation_refusal_retained:still_refused` or `preparation_refusal_retained:unavailable`. If a typed-refusal helper that does not know `preflight` refuses it as `invalid_request`, it is treated as `unavailable` (protocol mismatch) rather than a persisting cause, unless the retained refusal itself is `invalid_request`. A `{"ok":false,"error":"node_operation_refused"}` response from an older helper is not a transport failure but is treated as `node_failed:refused:legacy_unspecified` (there was a response but no evidence that nothing was run, certainty unknown), and the original attempt is held. A failure to serialize the response after execution is `executed_reply_failed` (unknown) and is not a refusal. The preparation diagnostics of submit are not evidence of execution or model success, and if no reservation can be made it returns exit code 1 and the queued task.

`return` (`returnResources` in `src/resource-return.ts`) returns the session resources of tasks whose termination and result custody are proven, sequentially (250 ms apart by default, at most 100). The only evidence of return is a new exact public `session.list`: it is confirmed as returned only when there is no session, or the row of the recorded original `endpointGeneration`/`endpointIncarnation` is `terminal:true` and `live:false`. `live:false` alone is not evidence. If the original incarnation is live, it records a per-attempt durable claim (`resource-return-close:N`) **before** dispatch, calls the public broker `session.close` exactly once with that key, the original tuple and `ifIdle:true`, and then confirms with a new listing. A claim without a response is never resent. `endpoint_stale` can also come from a transient pre-send failure, so it queries again immediately: a different incarnation is `not_ours`, a vanished one is confirmed returned, and an original incarnation still visible is `return_unknown`, and a later pass may make a new claim within the same limit. `busy` is a refusal before any effect, so it is claimed again only in later passes, up to 5 times. `operation_failed` with `lifecycle_legacy_history_ambiguous` (or an `operation_failed` with `outcomeCertainty:"unknown"` and no diagnostic) is treated as a deterministic refusal with no effect: it stops the pass for that node, reports `return_blocked_by_node`, and sends no close to that node until an audited `return-unblock` (read-only checks continue). The node block is checked in the same transaction as the close claim. Any other unclassified public refusal is not resent, and stops the remaining closes for that node in that pass. An existing `stop` claim is not resent and is settled with the same new evidence. A reservation that cannot be proven (authority missing, a reused ID, an unknown close outcome, a blocked node, an unreachable node) can be released with `return-override` (`{"operator","reason"}` required). This is not a return: it sends no close and queries a new listing once, and it is rejected if that listing shows the session ended (→ use `return`), live and not idle (a turn may be running), or the original incarnation live and idle with no close ever attempted (→ `return` first). It audits the operator identity, the reason, the query result and `observedGone:false`, releases the reservation only once, and reports the state as `released_by_operator_unconfirmed` (CLI exit code 3). `tasks`/`show` and the dashboard (tasks, nodes) show "may still be running on the node" until a later `return` has a new listing showing the session ended, and then record the confirmation (no second release) and it becomes `returned`. The operator identity is a self-reported value on top of local DB write permission and is not an authorization control. The node lease is only a wall-clock-based pacing indicator; mutual exclusion is handled by the per-attempt SQLite claim and the broker's incarnation check. An expired lease is taken over by token CAS without querying other tasks. Reclaiming descendant resources other than the host process is not proven by this contract.

Result custody is required before close in every attempt, with no exceptions. An attempt that `return` accepts has a recorded turn (`turnId`) and a confirmed end, so the turn ran and the node worktree may hold work that has not yet been recovered (this is also true for a turn that ended by failure or deadline excess, and `result` collects failed attempts too). A completed turn, an exact `failed` receipt, the two kinds of receipt-less confirmation, a late receipt, and records from an older version with no receipt evidence must all be held first with `result TASK_ID`, and the claim and confirmation transactions also require the manifest again. Getting the slot back without custody is possible only when it is proven that the turn did not run, and that is the existing `archive` path, not `return` (the no-session `never_started` classification, or a preserved before-send preparation refusal). A refusal report (`state:"refused"`) keeps the existing `reason` value and adds a stable per-precondition code `refusal` (`task_not_found`, `not_settled`, `custody_missing`, `custody_invalid`, `custody_binding_mismatch`, `authority_missing`, `ownership_missing`, `cancel_pending`, `unclassified`), and only when the task row was read (an empty, malformed or missing ID is only reported) it stores the same code and the classified diagnostic as a `resource_return_refused` audit event. If that task already has even one `resource_return_refused` row for the same refusal (same attempt, session, code, diagnostic), it is not stored again, however many audit rows have piled up in between, whether other events or other refusals occurred (even if refusals alternate). All refusals from one `return` call are stored in a single write transaction before node processing, so even when another writer holds the write lock the busy wait per call is at most once (busy_timeout 10 seconds), and in that case a storage failure does not change the report and is counted once as telemetry. The lookup for whether it is the same refusal scans the audit table once per call (the audit has no task index), and creates no new index or other schema object (open does not change the schema). A `resource_return_refused` row does not move the dashboard task `lastEventAt` (total elapsed time), but it does appear in the task timeline and in the window of the latest 100 audit rows of `observability`, so a single `return` with many refusals (up to 100 rows) can push earlier events out of that window.

### Explicit selected-output custody

`result TASK_ID [ARGV.json] --select RESULT.md --select selection.patch` (API:
`fleet.result(id, argv, ["RESULT.md", "selection.patch"])`) collects only exact relative
regular-file names. This is **selected custody, not full-workspace custody**. The node
branches before workspace diff/enumeration: unrelated large files, links and scratch
trees are not visited. The manifest has `custody: {kind: "selected", paths,
selectionDigest}`, a literal selected-path diff (not a whole-workspace diff), and the selected file bytes.
Export records retain that custody label. Without `--select`, full-workspace collection
is unchanged. Export's `--include`/`--require` remain post-collection filters, not custody selectors.

Submission can opt into the single automatic handoff with
`"autoCustody": {"paths": ["RESULT.md", "selection.patch"]}`. Sorted exact paths are validated and
bound in the immutable task input digest. The daemon collects only after a confirmed successful exact
runtime receipt with original exclusive session authority, using the existing selected-result path,
without a verifier. No field preserves the old operator-driven behavior. Unknown, failed, cancelled,
archived, live, unowned, receipt-less and approval-contract tasks cannot auto-collect. A durable shared
claim prevents concurrent/restarted uncertain collection; a missing manifest after a claim requires
operator investigation, never replay. Saved custody unblocks the existing resource-return path, not
approval, review dispatch, deployment or deletion. See [daemon custody and recovery](docs/daemon.md).

The sorted selection is durably bound to the task's exact attempt before tests or node
collection. Every later `result` request must repeat the same selection, including after
a failed collection or process restart. A changed or absent selector is `RESULT_CONFLICT`;
it never silently returns a broader/narrower cached manifest. Cached verification uses
the same selection before and after the explicit verifier; it does not attest to the
unselected workspace. Selected files must exist and satisfy the existing anchored
regular-file, link/reparse, excluded-path, 4 MiB/file, 16 MiB total and 1024-file limits.
Directories, globs, traversal, duplicate/case-alias selectors and missing/unsafe/oversized
files fail the entire request; there is no skip or fallback. Select a patch file explicitly
when a patch is a deliverable. This does not run a verifier unless ARGV is supplied.

### Operator commands: run, tasks filters, watch --all-active

```sh
bun src/cli.ts --local-node-id local run .local/task.json [--wait]
bun src/cli.ts tasks [--phase P[,P]] [--node ID] [--key-prefix S] [--since ISO] [--disposition K[,K]] [--subject ID] [--compact]
bun src/cli.ts watch --all-active [--interval MS] [--max-polls N]
```

- `run` goes through the same validation as submit, the `local_node_not_registered` guard, the preparation diagnostics and the measured-headroom admission (recorded `--resources` samples are refused), and then performs `start` once. Running again with the same caller/key looks at the durable state and handles the **same task**. A task waiting before reservation (queued) is measured anew and started after admission, and a task that is reserved but whose turn is not confirmed continues through `Fleet.start`. If a prepare/create/prompt claim already exists but its outcome is not recorded, it is not resent and is held as `blocked_unknown`. A different input (a changed digest) is refused. Only a run that holds the owner lease of the `operator-run` claim (owner, pid, host, expiry, renewed during start) performs the start. If another `run` of the same key holds a live lease, nothing is sent and 7 is returned, and that run's in-progress claim is not blocked as unknown. If the process that owns the lease has already exited on the same host (no pid) or the lease has expired (60 seconds by default), a recovery run takes over the lease and continues with `Fleet.start`, and a claim whose outcome is not recorded is held as `blocked_unknown` without a resend. After `Fleet.start` returns, it does not end with an error and decides the exit code from the durable task state, and the `operator-run` audit receipt is left, with the recorded turn, by the run that owns the start. If the prepare of `run` receives a proven (`before_send`) node refusal, it ends with a typed `node_refused:*` error (exit code 1) exactly like `start`, and the attempt stays as a pending refusal (`preparationRefusal` of `tasks`/`show`). The next `run` holds the lease and sends only a side-effect-free preflight through the same path as `start`, and if it passes, prepares a new attempt on the same reservation (the refusal-clearing transaction moves the `operator-run` claim and the lease to the new attempt together, so another `run` in between receives 7). If it does not pass, it ends again with 1 and `preparation_refusal_retained:*` is left in the reason.
- The exit codes (common to `run`, `run --wait` and `watch --all-active`) are defined only in the single `exitCodes` table of `src/operator-commands.ts`, and the CLI help and the table below render that table as it is (a test checks that they match, and checks each row with the real CLI). After the global options are parsed, the last stdout JSON line always has `exit` and `outcome`, errors included (a `--read-only` refusal, usage, input and store errors included). An error in the global options themselves returns only stderr JSON and 1. When several tasks are observed, it returns the code with the lowest rank (most severe), not the smallest number, so unknown (3) is not hidden by other results, and watch prints a per-task code summary line (`observation: summary`) at the end.

| exit | outcome | aggregation rank | meaning |
|---:|---|---:|---|
| 0 | `ok` | 9 | started and acknowledged (turn recorded); with --wait or watch: authoritatively settled successful execution (not artifact verification: a completed_unverified task reports 0 whatever its result, including one whose passing commands met an incomplete export awaiting operator acceptance, result.exportIncomplete, see export review); watch --all-active also exits 0 with an empty summary when no task was active, because only tasks seen active are watched (an already blocked_unknown task is not in the summary and is never observed; while other tasks are watched it can get a display-only progress line) |
| 1 | `error` | - | usage, validation or unhandled error (JSON on stderr); once the global options parse, every error of run or watch --all-active (including --read-only refusal) also prints {ok:false,error,exit:1,outcome:"error"} as the last stdout line; a proven before_send node refusal of prepare is such an error with its typed node_refused code: the attempt stays held as a retained refusal (tasks/show preparationRefusal), and the next run, like start, re-checks it by side-effect-free preflight only (still refused or unavailable: error again, reason preparation_refusal_retained:*) or, once passed, prepares a fresh attempt |
| 2 | `queued` | 8 | queued: no eligible node with measured headroom |
| 3 | `blocked_unknown` | 1 | blocked_unknown: a dispatch or observation outcome is unknown; held, never replayed |
| 4 | `failed` | 3 | failed, cancelled or archived (terminal without success; an archived task is reported, never run or started again) |
| 5 | `unavailable` | 5 | observation failed twice in a row, or the watch poll limit was reached; nothing marked or released |
| 6 | `approval_required` | 4 | approval_required: operator action needed |
| 7 | `in_progress` | 7 | another live run holds this task's start lease; this run sent nothing |
| 8 | `cancel_unknown` | 2 | cancel_unknown: a cancellation outcome is unknown; held |
| 9 | `not_started` | 6 | reserved but not started: local dispatch is disabled (rollback), or the admitted node is not admissible now (disabled, draining, not ready or route changed); nothing was sent and the reservation stays held |

Aggregation over several tasks (most severe first): 3 > 8 > 4 > 6 > 5 > 9 > 7 > 2 > 0.

- The default output of `tasks` is the same JSON array as before, and the filters apply to this JSON too. Only with `--compact` does it print a one-line summary (the first 12 characters of the ID, phase, node, the JSON-escaped key, seconds since submission, the execution outcome `executionOutcome` in the sixth column; for a disposed task a disposition mark in the seventh column, and for a task marked stalled or finished-unobserved a progress mark after that), and it does not print the prompt. `--since` is an ISO time with a time zone (inclusive, by the submit audit time), and a nonexistent date or time is refused. An option that needs a value always takes the next argument as its value, so even a key prefix that starts with `--` can be filtered. The filters work with `--read-only` too.
- `watch --all-active` observes, on a writable DB, every task it has ever seen as active, through the same `Fleet.inspect` path as `poll`. A task that another party (the fence of strict `poll` or the dashboard, a cancel, a settlement by another watcher) took out of active between polls is also reported with its status line and code. Only a failure or an incomplete question lookup in the read stage (connection, read_turn, question/approval lookup, execution receipt) is reported as `observation: unavailable`; it does not mark the task unknown or release it, and that read is recorded as abandoned and does not replace the failure fence of a strict poll running at the same time. A session/turn identity mismatch and a local error (including a missing original approval channel/authority, and a session/binding mismatch in approval discovery) hold the task as `blocked_unknown`, as in strict poll. The CLI registers no approval backend, so a task with an approval contract becomes 3 on this path. If the same task fails twice in a row, it stops observing that task and returns 5. Confirm with `poll TASK_ID`. A status line is printed only when it changes. The defaults are a 2000 ms interval and 1800 times, and the ranges are 10..60000 ms and 1..100000 times. `--all-active` may appear anywhere in the watch arguments. If there is no active task when observation starts, it returns an empty summary (`tasks: {}`) and 0. A task never seen as active (for example one already `blocked_unknown`) is not reported, so use `tasks --phase blocked_unknown,cancel_unknown` together for a status check.
- Coordinator call limits: the connection handshake (initialize/tools/list) and calls with effects use the node's `transport.timeoutMs` as it is (an integer from 5000 to 600000 ms; if omitted, POSIX 30000 ms and win32 120000 ms, `nodeRpcTimeoutMs`). Only the read-only observation calls (`read_turn`, `list_questions`) are bounded by `nodeObservationTimeoutMs` = max(that value, the OS floor). The OS floor is 180000 ms on win32 (`read_turn` of a running turn took 37 to 53 seconds on a Windows node, 28 to 62 seconds in earlier samples) and 30000 ms on POSIX (the default for a POSIX node is the same as before, and a read on a POSIX node whose `transport.timeoutMs` is under 30000 is raised to 30000). There is no separate setting key, and the observation limit is raised only through `transport.timeoutMs`. `transport.timeoutMs` is part of the node identity (digest). A remote node with a `workspaceTransport` must put the same value in the NODE_CONFIG of the target host as well, or the placement probe passes only that way (otherwise `workspace_transport_unverified`), and either way, before adding that key, first upgrade the target helper to a version that knows this key. Before rolling back to an older binary that does not know this key, remove the key from every node row and register again with `node add` (that binary refuses every node in placement and also refuses updates of that node). Requests with different limits on one connection do not overlap. If either limit expires the whole connection fails, so while a request with the other limit is in progress, a new request is refused as `too_many_requests` (before_send) before anything is written. Fleet's calls are sequential and never reach this path. A read whose observation limit expired is `blocked_unknown` in strict poll (the original attempt kept) and `OBSERVATION_UNAVAILABLE` in tolerant poll (the task unchanged), and no transmission is sent again. The execution deadline of a clawhip `run` is at most 120000 ms, so it does not cover the worst-case time of a win32 node (strict inspect = handshake 2×120 s + reads 2×180 s = 600 s, start = 4×120 s = 480 s). In that case clawhip records the call Fleet is still running as `unknown` (observation only, replay prohibited) and does not send it again, so check the result of such a node with `poll`/`watch`.
- `archived` (`task archive`) is a terminal state. `run`/`run --wait` of the same caller/key reports that task as 4 with no new admission, reservation or start, `watch --all-active` does not observe archived tasks, and if a task being observed is archived by another party, it reports it with that status line and 4. You can filter with `tasks --phase archived`, and the default `tasks` output includes archived tasks as before. archive refuses with `ARCHIVE_IN_PROGRESS` a task that has a live (unexpired) `operator-run` start lease, does not take or renew the lease of an archived task, and a late-failing observation read does not change an archived task either.
- There is no steer command. The current public contract has no original-turn CAS and no read-only result query, so it cannot be implemented safely. No steer is sent to any task, archived tasks included.

### Linking a review target (`subject`)

If you put `"subject": {"taskId": "IMPL_ID", "path": "fix.patch", "sha256": "HEX", "otherNode": true}` in the task input, a link is left saying this task targets one file of the **stored result** of another task. The state is the input itself: it is bound to the input digest and de-duplicated by caller/key, and there is no table, column, schema change or migration. `taskId` is the Fleet task ID, `path` is the normalized relative path recorded in the collected result (absolute and drive paths, `\`, control characters and empty, `.` and `..` segments are forbidden, at most 4096 bytes), `sha256` is 64 lowercase hex digits, `otherNode` is a boolean, and any other key is `INVALID_INPUT`. Using it together with `workUnit` is `INVALID_INPUT` regardless of the switch.

- Inside the `submit` transaction of the new task, it compares with the stored manifest of the target task (inline or externalised skeleton; the blob is not opened). No target is `SUBJECT_NOT_FOUND`; no stored result is `SUBJECT_NOT_COLLECTED` (submitting does not trigger collection, so collect first with `result`); a missing path, a deleted entry or a different SHA-256 is `SUBJECT_FILE_MISMATCH`; and if the input's caller/key points to the target task itself, `SUBJECT_SELF`. If `otherNode:true` but `required.nodeId` is the node of the target task, it can never be placed, so it is refused at once with `SUBJECT_NODE_PINNED`. Repeating the same input with the same caller/key does not check again and returns the same task.
- With `otherNode:true`, `selectNode` excludes the node of the target task with the reason `subject_node` and records it in the `selection` audit (`reserve`, and the preflight of `submit`/`run` does not probe that node, node-health gate). If there is no other node, it waits with `no_eligible_node`. The daemon publishes to `status.queue.admissible` only the nodes chosen by `preflightPlacement`, so when only the node of the target task was measured, it does not publish that task as admissible and does not probe that node (preflight `eligibility: subject_node`). However, the daemon's pre-filter does not look at this reason, so such a task is preflighted on every due pass and then deferred (cost only, bounded by the deferral backoff).
- `show REVIEW_ID` shows `subject` (the input value plus the current `phase` and `nodeId` of the target task). `show IMPL_ID --reviews` shows `reviews: [{taskId, phase, nodeId, path, sha256, resultDigest}]` (the latest 100 submissions, newest first, `reviewsOmitted` when over; `resultDigest` equals the `resultManifest.digest` that `tasks` shows for that task, and is null when it is not collected or when `tasks` shows a falsy result value instead of a digest). To find reviews it must read the JSON of every task row (an index would be a schema change), so `show` without `--reviews` does not look for reviews and reads only that task, as before. The output of a task with no link is the same as before. `tasks --subject ID` shows only tasks whose target is ID (no count limit) and works with `--compact` and `--read-only`.
- Even if the target task is later `task archive`d or `task dispose`d, the link is still read. The row is not deleted and the input does not change, so only the `phase` in `show` becomes `archived` and `reviews` is unchanged. The stored manifest remains after archiving, so a new submission targeting an archived task also passes the same check and is accepted. This link is not a verdict or verification, does not connect to a node, and does not send the target file bytes to the review task.
- A DB written by this tree has the same schema, so it opens in an older tree too, and queries (`tasks`, `show`) show the input's `subject` as it is. But the older tree does not know the `subject` key, so it refuses `start`/`run`/preflight of such a task with `INVALID_INPUT` (Unexpected field). So **if there is even one queued `subject` task that has not started**, `queue reconsider` of the older tree fails as a whole at the preflight of that task (queued tasks after it in row order are not reconsidered even if they have no link, repeating on every run), and the daemon queue pass also stops that pass at the same point (`queue_pass_failed`).
- **Step before rollback:** in this tree, start those tasks until no task is left in the JSON of `tasks --phase queued` that has `input.subject` (`queue reconsider` or `start TASK_ID`; if there is no node to place on other than the target node, register and enable another node). There is no command that removes a queued task that has not started: `task archive` accepts only placed failed/unknown tasks (a queued task gets `ARCHIVE_NODE`), and `task dispose` accepts only `completed_unverified` tasks. If such a task remains, do not roll back.

### Daemon: `daemon run` / `daemon status`

```bash
bun src/cli.ts --db .local/fleet.sqlite [--local-node-id ID] daemon run [--cycle-ms MS] [--lease-ms MS] [--queue-limit N] [--grace-ms MS]
bun src/cli.ts --db .local/fleet.sqlite --read-only daemon status   # 0 alive, 10 not running (does not overlap with 3=blocked_unknown in the operational exit table)
```

- It is the owner of the periodic work, of which there is only one per DB. While the daemon runs there is no need to poll elsewhere, and without the daemon every command works exactly as before.
- One cycle (5 seconds by default) does the following four things with a metadata-only index that does not read result bodies, prompts or observation evidence.
  - (a) Re-reviewing queued tasks: it re-checks never-attempted queued tasks with a new measurement and a read-only placement preflight (the same as `queue reconsider`), and publishes the tasks and nodes that can be admitted now to `status.queue.admissible`. It is within `--queue-limit` (default 10) per pass. **It neither reserves nor starts** (a reservation must be followed by a start, and a start is a prompt send). The task stays `queued` and holds no capacity, and `queue reconsider` places and starts it as before.
  - (b) Observation: it observes every observable task through the existing `poll` path (tolerant `Fleet.inspect`) in a fair round-robin. There is 1 concurrent call per task and 1 in-flight call per node (a placement probe is also one at a time per node), with a per-node interval (15 seconds for win32) and failure backoff. An observation whose digest equals an already applied observation writes no receipt or audit row. If `OBSERVATION_UNAVAILABLE` repeats for the same task after a real poll, the observation interval grows beyond the ordinary unchanged cap (120 seconds) up to `observeFailureMaxEveryMs` (default 15×, production default 30 minutes), and from the second consecutive poll failure it leaves a `daemon_note` `observation_repeated_failure_operator_recovery_required` once per attempt (it does not stop observing permanently or complete or retry the attempt).
  - (c) Selective custody (opt-in): only when the submit input has `autoCustody.paths`, for a task whose settlement and authority are proven, it collects only those paths as a selected `result` (no verifier). ### Review and report tasks (work-unit, off by default)

When turned on with `workunits enable --reason TEXT` (audit record), it accepts the input `"workUnit": {"role": "review"|"report"}`. The prompt must contain `fleet-review/report.md` (`ROLE_PROMPT_INSTRUCTION`: write the report as UTF-8 Markdown only to that file and change no other file or commit). If the base tree already tracks `fleet-review/`, the node refuses before preparation (`unsafe_path`). When recovered with `result TASK_ID` (no ARGV), it is recorded as `report_collected` if it is exactly one regular file `fleet-review/report.md`, an empty patch, valid UTF-8 and at least one visible character (4 MiB or less); otherwise `report_rejected` and the reason are left in the append-only table `task_deliverables`. However, if the report exceeds 4 MiB the node refuses the recovery itself (`unsafe_path`), so neither a result nor a record is stored (not `report_rejected`). **This is not verification.** The phase stays `completed_unverified` and `verified=false`, and the dashboard removes it from `outcome.unverified`, counts it as `reportsCollected`, and shows "Report collected · not verification" (warn). Nothing is recorded for cancelled, failed, archived, unknown, unterminated, unrecovered, or receipt-less tasks (a late receipt acceptance included), or when there is a test claim/`TEST_UNKNOWN`. An ARGV test and Clawhip collect are refused for a role task (`ROLE_NO_TESTS`). If the record is missing right after recovery, record it once with `deliverable TASK_ID` (DB only, no node contact). A storage or I/O error is `unavailable` and is not shown as a refusal or a success.

A review is submitted only as `"workUnit": {"role": "review", "subject": {"taskId": "AUTHOR_TASK_ID", "branch": "BRANCH"}}`. `baseCommit` (the head commit under review) must be a commit that the role-less Fleet task `AUTHOR_TASK_ID` of the same repoId made in its own Fleet workspace, that is, the stored result `outputHead` of that task (it must differ from the baseCommit of that task). The node of that task must have proven at result collection that this commit was newly created in the workspace (the head is a descendant of baseCommit, and every commit in baseCommit..head is unreachable from any ref (`refs/*`), the HEAD of another worktree, per-worktree refs (`refs/worktree/*`, `refs/bisect/*` and so on), and the reflog of the repository refs and of the main worktree HEAD; it is not proven if the repository root of the node is a linked worktree and not the main worktree; it does not apply to a result that merely moved HEAD to an existing commit left in such records, to a commit built on top of such a human commit, or to an older result without this proof). This proof is not put in the result manifest; it is obtained through a separate node query (`provenance`) outside the manifest and digest and left in its own audit row (`output_head_created`), so even after a rollback to 6b95dde the verified bytes of the result are the same. "Proven newly created" means "not reachable from the history recorded in this repository", not "written by Fleet": a human commit that exists only in the HEAD reflog of another linked worktree, an object brought in without a ref (for example, a commit where the agent ran `git fetch URL BRANCH` and then checked out FETCH_HEAD), and a commit in an expired reflog cannot be told apart from a newly created commit and are proven (this is also written in `reviewOrdering` of `workunits status`). Without proof it is refused with `NON_FLEET_COMMIT` (no operator bypass). Before preparation the node checks that `refs/heads/BRANCH` (the exact ref name, case included) is exactly `baseCommit`, and otherwise refuses with `identity_mismatch`. The prompt must also contain `VERDICT:` (`REVIEW_PROMPT_INSTRUCTION`), and unless the first line of the report (excluding one trailing CR) is exactly `VERDICT: CLEAN` or `VERDICT: NOT CLEAN`, or is followed by a space and a remainder that does not contain `CLEAN` (for example `VERDICT: CLEAN / NOT CLEAN`), it is `report_rejected: verdict_missing`. The record is bound to the repoId, branch, head commit, target task, evidence hashes (`report_sha256`, `manifest_digest`) and verdict. If the review session is the same as the session of the target task, it is `report_rejected: reviewer_not_independent`, and if the session of the target task is unknown, nothing is recorded (`not_ready`). `inputPackage` is not accepted for a role task (`INVALID_INPUT`). Even if the verdict is CLEAN, it is not verification and the phase stays as it is.

The commit-creation proof is requested from the node only once, at the **first** `fleet result` of a role-less task while the switch is on (one read-only `provenance` request), and left, in the same transaction as the result, as an `output_head_created` audit row or an `output_head_unproven` audit row with a reason (`not_created`: the node answered that it is not a new commit; `node_refused`: the node refused before any effect (for example an older-version node without `provenance`); `node_failed`: a transport failure, timeout and so on (with diagnostic); `reply_invalid`: any other reply). There is no path to ask again: the commit of an unproven result, or of a result collected while the switch was off or by an older Fleet version, cannot be reviewed, and a review submission is refused with `NON_FLEET_COMMIT`, with the recorded reason (or that the proof was not requested) in the message. **Ordering contract** (`reviewOrdering` of `workunits status`): the agent of the author task commits on a detached HEAD (`git switch -c`/`checkout -b` forbidden), and nobody may create a branch or other ref on that commit before its `fleet result`. The review branch is created after that. Otherwise it is `not_created`. If the switch is off, result collection is the same as code without work-units: there is no `provenance` request and no extra audit row. The HEADs of other worktrees are read from the list of `worktrees/` entries of the common git directory and passed through git stdin, so the number of worktrees does not hit the command-line length or the output cap.

The same check (cancel that task) is needed before a rollback too. The records stay and are not shown while the switch is off. If only the table exists and there are no rows, it is inconsistent and role submission and recording are refused, but queries work.

### Exporting result files (`export`)

```sh
bun src/cli.ts --db .local/fleet.sqlite export TASK_ID /absolute/NEW_DIR [--include GLOB]... [--require GLOB]...
```

- It takes files from the **single collected result** of a task, writes them to a new directory `NEW_DIR`, and also leaves `fleet-export.json` (task, attempt, node, repoId, baseCommit, outputHead, `manifestDigest`, `manifestStatus` (the state of the collected manifest, not the later verification state of the task), and per-file path, byte count and SHA-256). `manifestDigest` equals the stored result digest that `tasks`/`show` display.
- If a stored result exists, it does not connect to the node (the same bytes even if the node is off or the workspace has changed or is gone). If not, it first performs the ordinary `result TASK_ID` collection once, so it follows that refusal (`RESULT_NOT_READY`: before an authoritative end of execution, `ARCHIVED_TASK` and so on). `TEST_UNKNOWN` of the original verifier without a receipt is a stdout refusal with a code if its owner still holds the lease, and, if the owner is gone or there is no lease, a stderr JSON without a code, as in `result`. A node-side refusal is also a stderr JSON without a code. So a copy that the lane is still writing cannot be exported, and every export of the same task has the same bytes. A task disposed with `task dispose` is refused with `ARCHIVED_TASK` even if a stored result exists, as in `result`.
- `--include` (all files if absent) and `--require` are Bun.Glob patterns on the collected path (`*` does not cross `/`, and `review/**` means everything below). A pattern that starts with `!` (negation) is refused with `INVALID_INPUT`. For each `--require` pattern at least one file must match, and matching files are always exported. A deleted path is not exported.
- A refusal is a one-line stdout JSON `{ok:false, taskId, code, error}` and exit 1: `EXPORT_DEST_EXISTS` (the destination already exists: checked before collection, and also when another export or the like wrote to the same destination first during the export. However, something created in the short gap between the last check and the rename can be replaced under the rename rules: on POSIX an **empty directory**, on Windows a **file**. Otherwise it is refused), `EXPORT_DEST_PARENT`, `TASK_NOT_FOUND`, `EXPORT_REQUIRED_MISSING` (a list of patterns that did not match), `EXPORT_PATH_CONFLICT` (a collected file writes to the path of `fleet-export.json`), `EXPORT_WRITE_MISMATCH`, and a collection refusal with a code (`RESULT_NOT_READY`, `ARCHIVED_TASK` and so on). Any other error, such as a transfer failure, is a stderr JSON. On no failure is `NEW_DIR` created: it writes to a private (0700/0600) temporary directory under the same parent, reads it back and checks the SHA-256, and only then renames.
- It writes nothing to the DB except the ordinary result storage when collection is needed. It is refused with `--read-only`. **It is neither verification nor success**: phase and verified stay as they are. To close the task with a byte check, run `result TASK_ID ARGV.json` with the SHA-256 of `fleet-export.json` (since the bytes are the same as the stored collected result, it cannot fail because of an early copy). Otherwise record it with `task dispose`.

## Recovery and safety boundaries

The local rollback that permanently blocks new runs is `bun src/cli.ts --db EXISTING_DB --cap MATCHING_CAP rollback`. The API `FleetStore.enterRollback()/dispatchStatus()/assertDispatchEnabled()` stores the existing null-task audit `rollback_dispatch_disabled` once, idempotently, in an IMMEDIATE transaction. There is no new schema/epoch and no reenable/reset/release path, and it does not revert code, DB or patch. The writable CLI does this before Fleet/transport/input, and --read-only is refused before the store. It blocks **new claims** of submit/admission/reservation and of prepare/create/prompt/answer/cancel-abort/close/result-test/stop, even for already reserved tasks, with DISPATCH_DISABLED, and preserves the original IDs/keys/held state. node drain/disable blocks new selection and new task sends after reservation (prepare/create/approval-attach/prompt claims), and rollback blocks all new claims after reservation. An effect that may already have been claimed and delivered can complete with the original evidence, so this is not a remote atomic fence, exclusion of an old binary or forced termination of an existing run. An old restore without a marker is also not proven safe, and unknown is not bypassed with a new DB.

Even after rollback, exact public reads, local observation/audit/reconciliation and backup on a writable DB are allowed. A physical --read-only is a snapshot view and cannot store poll bookkeeping. The inspect connection requires only the real gjc_coordinator_read_turn/list_questions and does not require create/send. A missing required read or incomplete questions stay held, a missing SID stays unknown, and there is no synthetic settlement. An existing cached receipt is only an observation and is not authority for a new effect.

Here "schema unchanged" means no change to tables, columns, schemaVersion, migration, epoch or format. Only the `audit_global_kind` partial index for the new guard lookup (`audit(kind) WHERE task_id IS NULL`) is added in the existing writable constructor transaction, and readonly returns before DDL. A real EXPLAIN on 10,000 audit rows showed SCAN→indexed SEARCH, but this is neither a latency/speedup benchmark nor remote authority. 118 pass / 19.34 s and the bounded review 23 CLEAR cover the range before the index, and the post-index focused/full Mac/Windows runs are verified by the parent after the docs freeze. The preservation of G001/unknown is unchanged.

The new typed telemetry records the before_send|unknown of the real TransportError class only at the existing audit boundary. `FleetStore.backup(destination)` and the command above write one committed read snapshot with SQLite `VACUUM INTO`, page by page, into a new private staging directory next to the destination (0700, files 0600), and make **a consistent DB snapshot that includes the committed WAL**. It does not copy the main DB file as it is and does not checkpoint the source WAL. It preserves the task/attempt/session/turn, node snapshot, manifest, held slots, unknown reasons, pending operation ID/key/payload and audit as they are, and does no remote dispatch/replay, slot release or automatic startup. It does not load the whole DB into memory, so there is no size limit (the earlier `backup_size_limit_256_mib` is gone; there is a 300 MiB+ DB test), and it does not copy free pages, so a large DB right after `migrate results --apply` and before VACUUM can be backed up at once, and the backup is only as large as the live pages. While running, as much disk space as the staging file is needed in the destination directory. No root runtime dependency is added.

Only the staging copy is opened SQLite read-write, `PRAGMA journal_mode=DELETE` is applied, and the returned mode, `quick_check`, application_id and the match of `fleet_meta`/`user_version` are checked before closing. It copies and verifies the referenced blobs, fsyncs and hashes the staging file, and only then publishes it under the destination name with an exclusive hard link, so the destination name never points to an incomplete backup. There is no manual header edit or change of the source mode. It returns the SHA/size of the final main bytes, and there is evidence that restoring only that main exactly to a new file name reads without companions. However, there is a real measurement in which a 32 KiB SHM remains even after the normalizer and before the readonly open, so the self-contained main evidence is not extended to a guarantee of SHM cleanup. A normal writable `FleetStore` open switches the recovered copy to WAL, but an explicit read-only open does not.

In the success JSON, `path` is an absolute path, `sha256` is the SHA-256 of the actual snapshot bytes, and `bytes` is the byte count. The destination appears only through an exclusive link (mode 0600) and is `fsync`ed before publishing. The parent directory is also flushed (POSIX `fsync`, Windows kernel32 `FlushFileBuffers` on a `FILE_FLAG_BACKUP_SEMANTICS` directory handle) and `directorySynced` is returned. This value is false only on a POSIX filesystem that does not support directory fsync, and it does not guarantee power-failure durability of the filesystem/hardware or 0600 equivalence of a Windows ACL. If the destination or `-wal`/`-shm`/`-journal` already exists, it refuses and does not touch the existing bytes. A failure is reported as a bounded error (`backup_failed`, `backup_destination_exists`), and on failure it removes the staging directory, DB and `.results` directory this call newly created (if `.results` has an entry this call did not write, that directory and the staging are left, and the next retry reports `BACKUP_LEFTOVER`. Removal itself can fail, so do not use files left after an error as a backup and use a new destination). If a process was force-killed and could not clean up, running `backup` again to the same destination removes only the leftovers this tool can prove it made: a `DEST.backup-<token>` staging directory that has an `owner.json` recording the unique token of the name and the destination, host and pid, whose pid has already ended and that contains only files backup writes, and a `DEST.results` for which that record kept the identity (dev:ino:birthtime) and DEST was not published (only when it contains just the `<sha256>/data` blobs this tool writes (the bytes match the SHA-256 in the name) and `<sha256>.tmp-*` temporary directories, removed one file and one directory at a time, without recursive deletion). Other things that may be leftovers (a staging with no record or a broken record, the staging of a process that may be alive, a `DEST.results` whose process ended after creating it and before recording the identity, a `DEST.results` that contains other entries (files or directories with other names, symlinks, blobs with different bytes), and a `DEST.results` where the process ended after just before the publish (link) and only DEST was moved elsewhere (in this case the message tells you to keep it together with the moved DB, not to delete it)) are not touched, and it refuses with `BACKUP_LEFTOVER` (`backup_leftover: … remove exactly [paths…]`) telling you exactly which paths to delete. An already published DEST is never overwritten (`backup_destination_exists`). A backup contains sensitive source data such as prompts, answers and file contents, so keep protected local storage and access permissions. The hub's persistent poll sequence only keeps a late-arriving earlier query or error from overwriting the latest state, and does not replace remote execution ownership or the final-dispatch fence.
- A Coordinator re-call with the same key and same arguments is supported, but this adapter does not automatically re-call an unknown effect. Without a separate read-only key lookup, that limit is preserved. SDK `session.lookup` is creation-only and is not a lookup of another actor's Coordinator request.
- A slot is not released by a metadata terminal alone. It requires together the `agent_end` origin of the original runtime, the exact session/turn, an acknowledged and non-queued runtime ID, a live SDK idle, and a terminal session state. An end written with `report_status` is refused. Even this conservative decision is not a distributed exactly-once guarantee before verification on the real installed combination.
- If the workflow question lookup is incomplete, the end is not decided, and if a question remains, approval takes priority over a provisional completion. Waiting for approval → running observation can go back and forth in the same attempt, and the reservation is kept. An accepted answer alone does not mark consumption complete.
- It uses a detached worktree of an existing allowed repository with no new commit/branch. It does not reset/stash/delete the user's dirty files. Hooks, checkout filters, submodules, symlink input, sensitive files and path confusion are refused.
- A result file is opened pinned to a directory handle with `openat`, and a symlink/hardlink/path escape/oversize is refused. A digest is evidence of integrity and attribution, not proof of the honesty of a malicious node.
- The DB and local evidence may contain prompts/questions/answers/file contents. `.local` and `.gjc` are not deployed, and file permissions are restricted. Treat CLI/JSON results as untrusted text.
- The observation and verification evidence and the result bytes of `tasks`/`show` are summarized as digests/counts, and `poll` also does not duplicate the original prompt. The full file and test output are returned by an explicit `result` retrieval. A failed verification test and an unknown or refused task are kept as the nonzero exit code of that command.
- The input package is fully verified before reservation, and the node helper refuses a task if the declared OS/architecture differs from the actual process. A new POSIX work directory is created with 0700 before checkout. It does not infer that a Windows ACL is equivalent to a Unix mode.
- `verify` and `scripts/live-check.ts` each create a separate UUID evidence directory and print the real path. They do not overwrite the manifest/stdout/stderr of an earlier snapshot.
- Only a single hub is supported. There is no automatic lease expiry, ownership transfer, state deletion, guessed retry, or merge/push/deploy.
- Bun's `bun:ffi` is experimental per the official documentation. On Windows x64/Bun 1.4.0, real kernel32/ntdll creation, replacement, deletion and reading, rejection of hardlinks/junctions, and Git preparation of a full task ID were verified. Run it with `bun test test/windows-native.test.ts` after naming a separately approved existing exclusive directory in `FLEET_NATIVE_TEST_ROOT`. If it is not Windows or there is no root, this verification is skipped and is not success evidence. The writer's directory handle allows only READ|WRITE sharing in order to open the rename target and still refuses DELETE sharing. The sharing restrictions of the leaf/temp and the reader are kept. Windows arm64, adversarial concurrent writes, ACL equivalence and full operational acceptance are separate boundaries.
- Git commands isolate the user and system Git configuration and inherited `GIT_*` injection per call. A checkout filter in the repository itself is still refused. The Git program is chosen only by the trusted PATH resolution of `src/spawn.ts`: it looks for `git` (on Windows, `git.exe`/`.cmd`/`.bat` candidates) in absolute PATH entries (on Windows only drive-letter entries like `C:\…`; UNC `\\server\share\…` and `\\?\…` entries are not searched), skips the start directory, empty and relative PATH entries and entries inside the workspace/source repository (and their aliases), and uses the next trusted entry. If there is no trusted entry it is `git_unavailable`. On Windows it uses a per-command `core.longpaths=true` and a new exclusive short preparation path → Git worktree move, and does not change the final task/attempt path. It does not modify the system or user Git configuration. The JSON of the original runtime result lookup is passed with the public `--json-input-stdin` to avoid quoting conversion by SSH/the Windows shell.
- Every process start goes through one place, `src/spawn.ts`. A program name is resolved to an absolute path only from the trusted PATH (absolute entries only, excluding an entry equal to the working directory and entries inside the workspace/source repository or their aliases (symlink, junction, 8.3, case, UNC)), and on Windows a `git.exe`/`.cmd`/`.bat` planted in the working directory is not run. A relative-path program (`./x`, `bin/x`) and an absolute-path program inside an untrusted tree are refused. Git runs with the working directory as the trusted directory of the Git executable, with `-C <repository>`, `--no-pager`, hooks/fsmonitor/untracked cache/transport disabled, and a cleaned environment.

## API

On an installed combination where the end turn ID of the sidecar is empty, the durable terminal receipt of the original runtime command/turn is looked up with `turn.result` of the named SDK transport. A different ID, an unknown or an incomplete receipt is not end evidence. The existing `agent_end`, live idle SDK and complete question lookup conditions are kept. Result collection does not read or export the runtime-owned untracked `.gjc/`, and the refusal of other sensitive files and tracked runtime paths is kept.

```ts
import { FleetStore, Fleet } from './src/index';
const store = new FleetStore('.local/fleet.sqlite', 2);
try {
  const fleet = new Fleet(store, { localNodeId: 'local' });
  // store.putNode(explicitConfig); fleet.submit(input); await fleet.start(taskId);
  // await fleet.inspect(taskId); await fleet.answer(taskId, boundAnswer);
  // await fleet.result(taskId, explicitlyApprovedArgv); await fleet.stop(taskId);
} finally { store.close(); }
```

`src/contracts.ts` holds the schema v1 public input and state types. The low-level `FleetStore.observe` and `verifyResult` are for trusted adapter authors and are not an HTTP endpoint where a remote user injects arbitrary end evidence.

The public root exports the types `SdkUiApprovalBackend`, `SdkUiAttachment`, `SdkUiDispatchContext`, `SdkUiRouter`, `SdkUiRouterOptions` and `SdkUiApprovalOptions`. The application explicitly supplies the Router factory of the existing SDK and registers it with `new Fleet(store, { localNodeId: 'local', approvalBackends: [backend] })`. Choosing `approvalContract: 'sdk-ui-waiter-v1'` in the task input is included in the digest, and other contracts and unknown fields are refused. This is neither automatic approval nor a new SDK installation path.

`FleetStore.recordOperationReceipt(taskId, kind, operationId, receipt)` preserves only persistent evidence bound to the original task/attempt/claim. It allows only a re-record of the same receipt and refuses overwriting with a different value. After rollback, a late receipt of an effect that was already claimed can be preserved, but it does not approve running a new effect, releasing a slot or a remote termination. A read-only Store refuses even a re-record of the same receipt.

### Node health: stability history and placement gate

`NodeHealthHistory` (`src/node-health.ts`) is a durable history of real node probes, kept in the
fleet DB itself. Its tables are all `node_health_*` and are created with
`CREATE TABLE IF NOT EXISTS`; `user_version`, `application_id` and `fleet_meta` are never
touched, so a fleet build without node health still opens, writes and backs up the same DB
(rollback needs no migration; the extra tables are simply ignored).

**The switch.** Node health takes part in scheduling only while the operator switch stored in
the DB (`node_health_gating`, latest row) is on. It is off by default (no row), it is changed
only by the audited `node-health gating on|off APPROVAL.json` command, and no environment
variable, CLI flag default or config value turns it on. Every decision reads it once, first
(`FleetStore.nodeHealthGating()`, a plain read; a missing table or row is off).

```sh
bun src/cli.ts node-health show [NODE_ID]                      # read-only; allowed with --read-only
bun src/cli.ts node-health gating on APPROVAL.json             # {"operator":"…","reason":"…"}; audited
bun src/cli.ts node-health gating on --force APPROVAL.json     # override the stability guard; audited like on, prints forced: true
bun src/cli.ts node-health gating off APPROVAL.json            # already off: prints unchanged: true, writes nothing (no table, migration or row)
bun src/cli.ts node-health bootstrap NODE_ID --reason TEXT     # switch off: refused (exit 1, node_health_gating_off), opens and writes nothing
```

**Switch off (default): scheduling is exactly main.** `submitPlacement`, `reservePlacement`,
`reconsiderQueue`, pinned dispatch and operator `run` execute their unchanged pre-feature
bodies: no history is opened, nothing is probed or recorded, no lock is taken, and the
decisions, exclusions and audit events are identical to main for any node history. This is
proven by `test/node-health-differential.test.ts` (randomized seeded workloads over seven
nodes, replayed with no history and with empty, stable, mixed, recovering, random, corrupt,
toggled histories and a concurrent producer, and against a pristine main tree via
`FLEET_BASE_ROOT`; a negative control shows the harness detects the gate when it is on).
History is produced only by the `ui` hub producer (not `--read-only`, not `--no-probe`, and only
while the switch is on; one history, every enabled node every 20 s, stream samples stamped on
receipt as evidence) and by an explicit `node-health bootstrap` (switch on only; while off it is
refused with `node_health_gating_off` before the history is opened). A `ui` started with the switch
off opens the history read-only: it creates no table, writes no row, probes nothing and schedules
no producer. A running producer re-reads the switch every tick and stops for good once it reads
off (or cannot read it); after `gating on`, (re)start `ui`. `ui --read-only` and `node-health show` open the history
read-only (`query_only`); on a DB without the tables they show empty history and create
nothing. While off, the dashboard (page, `/api/state`, websocket state) shows no node health at
all: no `nodeHealth`, no `nodes[].health`, identical to the dashboard without node health;
`node-health show` still reports the stored history and the switch.

**Switch on.** Each decision (submit, reserve, each queue reconsider candidate, pinned
dispatch, `run`) first probes every hard-eligible node (Coordinator tools/list, then the
guarded Broker `sdk session list --attach-only`; nodes in parallel, each probe bounded by the
preflight timeout, default 10 s), THEN takes fresh resource samples, records one observation per
probed node, runs the unchanged preflight on the fresh samples, and excludes automatic
candidates that are not stable (`node_unstable` plus the cause in the durable selection audit).
The probes therefore add up to two timeouts of latency per decision, but they never age the
samples admission judges. A pinned dispatch onto a ready but unstable node is reserved with a
`node_health_warning` event in the same transaction. Results carry `health` (`mode: "enforce"`
and the per-node decisions; the CLI shows it as `placement.nodeHealth`). A health error (a
corrupt state row, `SQLITE_BUSY`, an unopenable history) never aborts the decision: it fails
closed with `node_health_unavailable` (automatic candidates excluded, the task stays queued;
a pinned ready node is still reserved with a warning). The result reports it as
`nodeHealth.error` = `{code, stage, errorClass}` (fixed code, Fleet-defined stage, error class;
never the error text, never stored); a failed sidecar copy of a pinned warning is reported the
same way as `healthWarningMirrorError` (`node_health_mirror_failed`, stage `mirror`). Samples from `--resources` files are
admission input only and never health success evidence. A resource-return node block
(`return-unblock`) is a separate concept: it never marks a node unstable, and node health never
blocks returns. Archived tasks keep their events and exclusions.

**Switching on with little history: exactly what happens.**
1. A node with no history is `no_history` and is not eligible for automatic selection. A node
   with some history needs `consecutive` (3) counted probes, or `recoveryConsecutive` (5) after
   any failure, before it is stable.
2. If no enabled node is stable, every automatic decision excludes every node at once: the task
   is queued (not failed) with each node's cause in its selection audit, and `queue reconsider`
   admits it once a node becomes stable.
3. Pinned dispatch (`required.nodeId`) onto a ready node still works, with a
   `node_health_warning`.
4. A node without a guarded `sdkTransport` (no `sdkTransport`, or an ssh one whose remote
   command cannot be guarded) can never observe the Broker list dimension, so it can **never**
   become stable (`unobserved:brokerSessionListOk`) and stays excluded from automatic selection
   for as long as the switch is on, although main schedules it. `show`, the gating preview and
   the dashboard mark it (`neverObservable`, "… unobservable · permanently excluded from auto-assignment once applied").
5. Guard: `gating on` without `--force` is refused (exit 1, `node_health_not_stable`) while any
   enabled, non-draining node is not stable, and prints the preview (per node `stable`,
   `wouldBeExcluded`, `failingDimensions`, `consecutiveGood/required`, `neverObservable`, plus
   `allExcluded`). With `--force` the switch is set anyway and the preview is printed with it.
6. Getting to stable: nothing is recorded while the switch is off (`bootstrap` is refused and
   `ui` does not produce), so a DB without earlier history needs `gating on --force`, then one
   `node-health bootstrap NODE_ID` per node (4 probes / up to 130 s fresh, 6 / 210 s recovering);
   automatic selection excludes the nodes that are not yet stable meanwhile. With the switch on, a `ui` started after `gating on` needs about 80 s (fresh) or 160 s
   (after a failure) of producer probes. With the switch on, each CLI
   decision also probes and records, but as a one-shot process it only counts under the
   restart bound below (129 distinct processes for a fresh node), so do not rely on it.
7. `gating off` restores main's decisions from the next decision on.

**Rule.** A probe with any dimension `false` (Coordinator reachable, Broker session list, hub
resource sample) resets the node: `count = 0`, and from then on `recoveryConsecutive` counted
probes are needed. A good probe counts when it is the first after a reset, when its writer (one
`NodeHealthHistory` instance) proves with its own monotonic clock that it is at least
`spacingMs` (default 30 s) after one of its own probes since the last counted one, or when good
probes from `restartFallbackWriters` (default 64) distinct writers were recorded since the last
counted one. Every dimension must also have been observed `true` since the reset. Automatic
admission additionally needs the decision's own probe (`decision_probe_required` otherwise).
No cross-process elapsed time is ever used; time only grants credit, and a failure always
resets. Wall time is display only.

**Resource evidence reads no wall clock.** A hub sample is success evidence only when the
receiving process stamped it with the history's own monotonic clock on receipt, and only while
its monotonic age is within the admission policy's `maxSampleAgeMs`. The dashboard stamps each
stream sample on receipt; the CLI stamps each fresh sample on receipt through the
`sampleResourcesOnce` per-sample callback (never `--resources` files); bootstrap stamps its
`sampleResources` result. A wall-stamped sample can only report a failure (`ok: false`). The
unchanged base resource admission (`src/admission.ts`) still judges sample age with the wall
clock; that check is admission input, not health evidence.

**Bounds** (default policy). One long-lived writer at cadence `c` is stable after
`1 + (need - 1) * ceil(30 s / c)` probes (60 s fresh, 120 s after a failure at `c` = 30 s; 80 s
and 160 s at the `ui` cadence of 20 s), plus one cadence per count when other writers
interleave. Under any restart pattern without a failure, a node is stable once good probes from
`1 + (need - 1) * 64` distinct process lifetimes were recorded (129 fresh, 257 recovering;
21.5 / 42.8 min at a 10 s crash loop). The single trust assumption is that a process's
monotonic clock never runs faster than real time. A slow, frozen or backward clock, a restart
or a copied database can only delay stability. Without a producer, an outage that falls
between decisions is never observed: run `ui` as the producer before relying on the switch.

**Operations.** While the switch is on, the `ui` producer sends two remote calls per enabled
node every 20 s (a Coordinator tools/list and a Broker `sdk session list --scope all`), whether
or not anyone is viewing, including Windows nodes; this load on real hosts is not measured. Both wait in the
`ui`'s per-destination SSH queue, so they never overlap another login of this process to the
same host (the Coordinator session holds the queue for its whole tools/list). A refused
`gating on` is decided on the read-only history view and creates no table. The switch state
lives in the DB: run `node-health gating off` before rolling back to a build without node
health, otherwise the switch silently comes back on when this code is deployed again.

Not exercised: real `performance.now()` behaviour across a host suspend or VM pause, real
cross-host SQLite sharing, and the producer's probes against real hosts.
